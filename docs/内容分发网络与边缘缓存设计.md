# CDN 与边缘缓存设计

> 文档状态：代码实现与运维约定并存
>
> 最后核对：2026-09-01
>
> 事实边界：Purge 调用可由代码验证；EdgeOne 控制台、Nginx 和发布预热策略必须以实际部署配置为准

## 设计目标

当前前台是 Nuxt SSR，部署在 Nginx 后面，并通过腾讯云 EdgeOne 提供边缘加速。CDN 设计目标是：

1. 静态资源尽量命中边缘节点，降低源站带宽和延迟。
2. 文章详情 HTML 可以缓存，但文章更新、删除、标签变更后必须及时清理。
3. API 不被 CDN 缓存，避免用户态和后台数据错乱。
4. 源站 IP 尽量不暴露真实业务响应特征，降低被绕过 CDN 直打的风险。
5. 缓存策略由 Nginx/EdgeOne 统一管理，避免 Nuxt、Nginx、CDN 多层 Cache-Control 冲突。

## 请求链路

```text
浏览器
  -> EdgeOne CDN
      -> Nginx
          -> portal-web Nuxt SSR
          -> meta-api Go 后端
          -> admin-ui 静态后台
```

不同流量类型：

| 类型 | 入口 | 缓存策略 |
|---|---|---|
| Nuxt 静态资源 | `/_nuxt/*`、图片、CSS、JS、wasm | 长缓存，CDN 命中优先。 |
| 前台 HTML | `/`、`/article-detail/*`、`/tag/*` 等 | 可按页面规则缓存，文章详情需要主动 Purge。 |
| 前台 API | `/api-backend/user/*` | 不缓存。 |
| 后台 API | `/api-backend/admin/*` | 不缓存。 |
| 后台静态资源 | `admin.liubing.xyz` 静态文件 | 可缓存。 |
| guard wasm | `/guard/guard_core.js`、`/guard/guard_core_bg.wasm` | 可缓存，但发布时必须兼容 build_hash 灰度。 |

## Nuxt SSR 与缓存边界

`portal-web/nuxt.config.ts` 中已经明确：

> 页面缓存策略统一交给 Nginx / EdgeOne 管理，避免 Nuxt 与网关输出重复 Cache-Control。

这意味着 Nuxt 不负责决定文章 HTML 缓存多久。Nuxt 只负责 SSR 输出 HTML，具体缓存由 Nginx 和 EdgeOne 控制。

这样做的好处：

1. 缓存策略集中在网关和 CDN，方便线上调整。
2. 避免 Nuxt 输出 `no-cache`，CDN 又强制缓存，排查困难。
3. 文章变更时由 Go 后端主动 Purge CDN，链路清楚。

## EdgeOne 规则设计

建议在实际 EdgeOne 控制台核对并保留证据的规则包括：

| 规则 | 作用 |
|---|---|
| 静态资源加速 | 对 JS、CSS、图片、wasm 等静态资源设置长缓存。 |
| 回源鉴权 Header | 给源站附加自定义 Header，用于识别来自 CDN 的回源请求。 |
| 前台 API 不缓存 | `/user/*` 或反代后的前台 API 不应被缓存。 |
| 后台 API 不缓存 | `/admin/*` API 不应被缓存。 |
| 文章详情 HTML 缓存 | 建议单独为 `/article-detail/*` 新建页面缓存规则；是否已经生效不能仅从代码仓库判断。 |

这些属于运维配置，不是 Go 代码能够强制保证的行为。面试时应展示实际规则截图、导出配置或请求响应头，不能把“建议配置”直接说成“线上已经配置”。

### 为什么文章详情规则要单独写

之前已经遇到过一个关键问题：只按后缀名匹配静态资源，例如 `.js`、`.css`、`.jpg`，无法覆盖 Nuxt SSR 生成的无后缀页面：

```text
/article-detail/188209396017266697
/tag/Golang
/time-line
```

这些路径没有文件后缀，不能被“后缀匹配静态资源规则”命中。因此文章详情 HTML 如果要缓存，应该单独写路径规则，例如：

```text
Path match: /article-detail/*
Cache: enable
TTL: 根据内容更新频率设置，例如 1h 或 1d
```

不建议把文章详情混入静态资源规则，因为二者失效机制不同：

| 类型 | 失效方式 |
|---|---|
| 静态资源 | 文件名带 hash，发版后 URL 变化，天然长期缓存。 |
| 文章 HTML | URL 稳定，内容会变，必须主动 Purge。 |

## API 不缓存

API 必须明确不缓存：

| API | 原因 |
|---|---|
| `/user/article/view-log/:id` | 浏览量打点是写操作，必须直达后端。 |
| `/user/share/precheck` | guard 信封含 nonce，不能缓存。 |
| `/user/share/consume` | 一次性 token 消费，不能缓存。 |
| `/user/comment/*` | 用户态和实时评论状态，不应由 CDN 缓存；公开读接口可使用后端内部 Redis 快照。 |
| `/admin/*` | 后台权限接口，必须不缓存。 |

建议 API 响应和 CDN 规则都使用：

```text
Cache-Control: no-store, private
```

当前 view-log 和 jsonshare handler 已显式设置 `Cache-Control: no-store, private`。

## Go 后端主动 Purge

`meta-api/pkg/cdn` 封装 EdgeOne Purge API。文章相关操作会调用：

```go
cdn.PurgeArticles(articleID)
```

内部拼接目标 URL：

```text
{EDGEONE_PURGE_DOMAIN}/article-detail/{articleID}
```

并调用 EdgeOne `CreatePurgeTask`，随后轮询 `DescribePurgeTasks`，直到任务成功或超时。

触发 Purge 的场景：

| 场景 | 原因 |
|---|---|
| 文章更新 | 标题、正文、摘要、标签变化后旧 HTML 不能继续命中。 |
| 编辑草稿发布 | 实际更新已发布文章，需要清理文章详情 HTML。 |
| 文章删除 | 防止 CDN 继续返回已删除文章。 |
| 标签调整 | 文章详情页展示标签名，需要清理受影响文章。 |

### 为什么删除文章前先 Purge

删除文章时当前策略是先 Purge CDN，再删数据库。如果 Purge 失败，保留数据库记录并返回错误。这样可以避免后台显示删除成功，但 CDN 仍长期返回旧 HTML 的问题。

这是一个偏保守的一致性选择：宁愿删除失败，也不让边缘节点继续展示源站已删除的数据。

## CDN 客户端降级策略

`pkg/cdn.New` 初始化时依赖：

| 环境变量 | 说明 |
|---|---|
| `EDGEONE_SECRET_ID` | 腾讯云 SecretId。 |
| `EDGEONE_SECRET_KEY` | 腾讯云 SecretKey。 |
| `EDGEONE_ZONE_ID` | EdgeOne Zone ID。 |
| `EDGEONE_PURGE_DOMAIN` | 文章详情 Purge 使用的域名。 |

如果配置缺失：

| 环境 | 行为 |
|---|---|
| 非生产 | CDN client disabled，调用 Purge 直接返回 nil，方便本地开发。 |
| 生产 | Purge 不可用时返回错误，避免文章变更在未清 CDN 的情况下被提示成功。 |

## guard wasm 的 CDN 缓存

WASM 发布流程期望把构建产物放到：

```text
portal-web/public/guard/
  guard_core.js
  guard_core_bg.wasm
  guard_hmac_build_hash.txt
  wasm_sha256.txt
```

当前仓库中没有检出上述 `public/guard` 构建产物，它们可能由独立构建或部署流程注入。浏览器协议期望通过固定路径加载：

```text
/guard/guard_core.js
/guard/guard_core_bg.wasm
```

由于路径固定，CDN 和浏览器可能缓存旧版本。发布时必须遵守：

1. 先构建 Rust WASM。
2. 把新产物放入 `portal-web/public/guard`。
3. 将 `guard_hmac_build_hash.txt` 中的 hash 加入后端 `guard.build_hashes`。
4. 灰度期间同时保留旧 hash 和新 hash。
5. 清理或预热 CDN 中 `/guard/guard_core.js` 和 `/guard/guard_core_bg.wasm`。
6. 等缓存自然过期或确认旧版本不再访问后，再删除旧 hash。

如果只保留新 hash，而用户微信或浏览器仍缓存旧 wasm，就会出现 `HMAC_FAIL`，浏览量和 JSON 分享都会失败。

## 微信内置浏览器缓存

微信内置浏览器可能对 JS/WASM 和页面资源有自己的缓存行为。即使已经在 CDN 平台 Purge，用户端仍可能短时间加载旧资源。

应对策略：

1. 后端 build_hash 白名单保留多版本，这是最重要的兼容手段。
2. WASM 文件可以考虑发布为带版本路径或文件名，例如 `/guard/{build_hash}/guard_core_bg.wasm`。
3. `guard_core.js` 引用对应版本 wasm，减少固定路径缓存问题。
4. 对固定路径保留短 TTL，避免微信缓存长期滞留旧版本。

当前项目仍使用固定路径，所以灰度期间保留旧 hash 是硬约束。

## 静态资源预热

当前 `portal-web` 仓库没有 EdgeOne 静态资源预热脚本，因此预热属于待补齐的发布能力，不能描述为已经实现。若后续增加脚本，应读取 Nuxt 3 实际构建输出目录（通常为 `.output/public`，以当次构建配置为准），生成带部署域名的 URL 列表后提交 EdgeOne。

设计要点：

| 点 | 说明 |
|---|---|
| 批次大小 | 根据 EdgeOne API 限额配置，不能在没有脚本和运行记录时宣称线上固定为 50。 |
| 并发 | 可通过环境变量控制，例如 `EDGEONE_PREFETCH_CONCURRENCY=2`。 |
| 失败重跑 | 失败 URL 写入文件，下次运行自动只补跑失败 URL。 |
| 校验 | 预热后可用 HEAD 校验 `eo-cache-status`。 |
| 全量预热 | 清空或删除失败文件后执行全量。 |

预热适合静态资源，不适合替代文章详情 HTML 的 Purge。文章内容变更仍应由后端按 URL 精确清理。

## Nginx 配置原则

Nginx 层主要承担：

1. TLS 终止。
2. 域名路由。
3. 反向代理到 Nuxt、Go 后端和后台静态资源。
4. 日志按域名和流量类型拆分。
5. 默认 server 拒绝未知域名或 IP 直连。
6. 输出安全响应头和缓存头。

对于 IP 直连，建议 default server 使用尽量少的信息返回，例如：

```nginx
server {
    listen 80 default_server;
    listen [::]:80 default_server;
    server_name _;
    return 444;
}

server {
    listen 443 ssl default_server;
    listen [::]:443 ssl default_server;
    server_name _;
    ssl_reject_handshake on;
}
```

不过要认识到，网络空间测绘并不只看 HTTP 响应，还会看 TLS、端口、证书、响应时间、源站和 CDN 回源行为等特征。隐藏源站需要多层措施：

1. 云防火墙只允许 CDN 回源 IP 访问 80/443。
2. 源站校验 CDN 回源 Header。
3. 默认 server 不返回业务特征。
4. 后台和管理接口不暴露源站直连。

## 源站保护

理想的源站保护策略：

| 层 | 措施 |
|---|---|
| 云防火墙 | 只允许 EdgeOne 回源 IP 段访问 Web 端口。 |
| Nginx | 默认 server 拒绝未知 Host，业务 server 校验回源 Header。 |
| 应用 | 管理接口有 JWT 和 TOTP，敏感接口限流。 |
| 日志 | reject/default 流量单独记录，便于观察扫描。 |

腾讯云轻量应用服务器防火墙规则数量有限，如果 EdgeOne 回源 IP 很多，不能逐条维护时，可以考虑：

1. 使用安全组或云防火墙支持的 IP 段能力。
2. 在 Nginx 做回源 Header 校验作为第二道门。
3. 使用反代隧道或只暴露 CDN 可达的内网入口。

## sitemap 缓存

Nuxt sitemap 使用 `@nuxtjs/sitemap`，动态数据源：

| 数据源 | 说明 |
|---|---|
| `/api/__sitemap__/articles` | 从 Go 后端分页拉取文章列表。 |
| `/api/__sitemap__/tags` | 从 Go 后端拉取标签列表。 |

Nuxt 内部 sitemap 缓存由 `/api/_revalidate` 清理。Go 后端文章新增、更新、删除、标签调整后会刷新 sitemap 内部缓存，让爬虫尽快看到最新 URL 和 lastmod。

注意：sitemap 缓存清理和文章 HTML CDN Purge 是两件事。

| 动作 | 影响 |
|---|---|
| sitemap revalidate | 影响 `/sitemap.xml` 输出。 |
| EdgeOne Purge | 影响 `/article-detail/{id}` HTML 缓存。 |

## 当前设计风险

| 风险 | 说明 |
|---|---|
| 固定路径 WASM 缓存 | 微信和浏览器可能继续加载旧 wasm，必须保留旧 build_hash。 |
| Purge API 失败阻断后台操作 | 这是保守策略，保证一致性，但会影响后台发布体验。 |
| 接口失败不等于数据库回滚 | 删除文章是在删库前 Purge；更新文章等场景可能已经提交 MySQL 后才 Purge，Purge 失败时接口返回错误，但业务数据可能已经成功，需要幂等重试和明确提示。 |
| 页面 HTML 缓存规则遗漏 | 无后缀 SSR 页面不会命中后缀规则，需要独立路径规则。 |
| 源站 IP 仍可能被识别 | 仅返回 444 或拒绝握手不足以彻底隐藏源站，还需防火墙和回源鉴权。 |
| 多层 Cache-Control 冲突 | Nuxt、Nginx、CDN 任何一层输出冲突都可能导致缓存表现不符合预期。 |

## 后续优化方向

| 方向 | 说明 |
|---|---|
| WASM 版本化路径 | 将 `/guard` 改为 `/guard/{build_hash}`，从根上减少固定路径缓存问题。 |
| 幂等 Purge 重试 | 先提供可重复执行的后台重试、失败告警和明确任务状态，解决当前规模下最直接的恢复问题。 |
| 持久化 Purge 任务（条件式） | 只有同步重试仍无法满足可靠性目标时，才评估任务表或 Outbox，避免为低频后台写操作过早引入 worker。 |
| EdgeOne 规则文档化 | 把 CDN 控制台规则导出为文档或 Terraform，降低手工配置风险。 |
| 源站访问白名单自动化 | 自动同步 EdgeOne 回源 IP 段到防火墙或 Nginx allowlist。 |
| 缓存命中率监控 | 监控 `eo-cache-status`、回源比例、Purge 失败率、静态资源 404。 |
| HTML stale-while-revalidate | 对部分低风险页面可用 SWR，文章详情仍配合 Purge 保证一致性。 |
