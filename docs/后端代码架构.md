# 后端代码架构

> 文档状态：当前实现
>
> 最后核对：2026-09-01
>
> 主要事实来源：`bootstrap/`、`app/di/`、`app/router/`、`app/handler/`、`app/service/`、`app/model/`

## 技术栈

当前 `meta-api` 是一个 Go 单体后端，核心技术栈：

| 技术 | 用途 |
|---|---|
| Gin | HTTP 路由和中间件。 |
| GORM | MySQL ORM 和模型迁移。 |
| go-redis | Redis、Sentinel、Pipeline、Lua 限流。 |
| dig | 依赖注入容器。 |
| zap | 结构化日志。 |
| robfig/cron | 定时任务，例如浏览量回写。 |
| Sonyflake | 生成全局唯一业务 ID。 |
| Tencent Cloud SDK | EdgeOne CDN Purge。 |
| COS SDK 封装 | 文章图片上传和删除。 |

## 分层结构

项目按典型后端分层组织：

```text
main.go
  -> bootstrap
  -> app.Application
      -> di.BuildContainer
      -> router.SetUpRouter
          -> handler
              -> service
                  -> model
                      -> MySQL / Redis / 外部客户端
```

目录职责：

| 目录 | 职责 |
|---|---|
| `bootstrap` | 配置、日志、MySQL、Redis、雪花 ID、cron、HTTP server、KeyManager 初始化。 |
| `app/router` | Gin 路由注册和中间件组织。 |
| `app/handler` | HTTP 参数绑定、响应编码、状态码转换。 |
| `app/service` | 业务编排、缓存维护、外部服务调用、事务边界设计。 |
| `app/model` | MySQL 表模型和数据库读写。 |
| `common` | 通用能力：cache key、guard、middleware、rate limit、utils、types。 |
| `pkg` | 外部基础设施封装：CDN、COS、邮件、短信、sitemap。 |
| `config` | 配置结构和 YAML 配置。 |
| `docs` | 技术设计文档。 |

## 为什么当前仍适合单体

当前博客系统功能不少，但访问规模、团队规模和部署复杂度仍适合单体：

1. 业务边界清楚，但跨模块一致性要求高，例如文章更新同时影响 Redis、图片引用、CDN、sitemap。
2. 单体部署简单，个人项目运维成本低。
3. Go 单体可以通过包边界实现领域隔离，不必为了“架构复杂度”提前拆服务。
4. 数据库和 Redis 当前仍是共享基础设施，拆成微服务会先引入分布式事务和事件一致性问题。

更合理的路线是：先把单体内部模块边界打清楚，再逐步抽出高独立度模块。

## 依赖注入

项目使用 `go.uber.org/dig` 组织依赖。

DI 注册分为三层：

| 层 | 文件 | 说明 |
|---|---|---|
| 基础设施 | `app/di/base.go` | Config、Logger、IDGenerator、MySQL、Redis、KeyManager、CDN、COS、sitemap、guard store/engine。 |
| Model | `app/di/layers.go` | admin、article、comment、link、siteDynamic、tag、user model。 |
| Service | `app/di/layers.go` | admin、article、comment、jsonshare、link、siteDynamic、tag、userauth、viewlog service。 |
| Handler | `app/di/layers.go` | 各领域 HTTP handler。 |

好处：

1. Router、Application 和 Service 使用同一套单例依赖，避免重复构建容器导致实例发散。
2. 单测可以针对 service 或 model 注入 fake 依赖。
3. 新增领域模块时，只需要补 model、service、handler 构造函数和 DI 注册。

需要注意的是，DI 不是为了隐藏依赖。当前构造函数仍然显式声明依赖，例如 article service 需要 article model、tag model、Redis、CDN、COS、sitemap 等，这能体现业务编排复杂度。

## 启动生命周期

启动流程由 `bootstrap` 和 `app.Application` 共同完成。

### bootstrap 阶段

主要初始化：

1. 读取运行时环境变量。
2. 加载 YAML 配置和配置文件监听。
3. 初始化 zap logger。
4. 初始化 Sonyflake ID 生成器。
5. 初始化 cron。
6. 初始化 MySQL，并执行 `AutoMigrate`。
7. 初始化 Redis Sentinel 客户端。
8. 初始化 KeyManager，用于 guard RSA 私钥。

MySQL 和 Redis 连接都有重试逻辑，并且连接失败时会显式关闭已创建的连接池，避免重试过程中泄漏 fd 或后台 goroutine。

### Application 阶段

`app.NewApp` 构建 DI 容器，解析 article service，然后注册：

| 任务 | 时机 | 说明 |
|---|---|---|
| `WarmUpCache` | 启动时 | 从 MySQL 在临时 Key 中重建文章时间和浏览量 ZSet，完成后事务性切换并移除正式 Key 的 TTL。运行期丢失时由读接口自动回源并重建。 |
| `RegisterCronJobs` | 启动时 | 注册浏览量定时回写任务。 |
| `PersistViewCount` | 停机时 | 优雅退出时把 Redis 浏览量回写 MySQL。 |

启动 HTTP server 前会先注册 cron 任务，再启动 cron 调度器，避免启动时序交错。

### 优雅停机

收到 SIGINT 或 SIGTERM 后：

1. 停止 HTTP server，不再接受新请求。
2. 停止 cron，避免定时任务和停机任务并发写浏览量。
3. 执行停机任务，例如浏览量回写。
4. 关闭配置监听、KeyManager、MySQL、Redis、Logger。

这条链路体现了一个关键点：浏览量这种缓存在停机时必须兜底落盘，否则容器重启可能丢失最近增量。

## 路由架构

路由入口在 `app/router/router.go`：

```text
/admin
  /account-login
  /bind-dynamic-code
  /verify-dynamic-code
  /refresh-token
  /logout
  /auth/article/*、/tag/*、/link/*、/site-dynamic/*
  /auth/comment/*、/user/*、/about-me

/user
  /article/*
  /tag/*
  /link
  /site-dynamic/list
  /about-me
  /bug-feedback
  /comment/*
  /auth/oauth/*
  /share/*
```

全局中间件：

| 中间件 | 说明 |
|---|---|
| Timeout | 默认 3 秒，部分上传、OAuth、文章更新删除等接口有独立超时。 |
| GinLogger | HTTP 访问日志。 |
| GinRecovery | panic 恢复并记录日志。 |

`TrustedPlatform` 使用 `X-Client-IP`，同时只信任 Docker 内网代理段 `172.16.0.0/12`，避免任意客户端伪造 IP。

## Handler 层职责

Handler 应该保持薄：

1. 从 path、query、body、header、cookie 取参数。
2. 做基础格式校验。
3. 调用 service。
4. 将 service 的业务结果映射成 HTTP 响应。

例如 view-log handler：

1. 从 path 取 articleId。
2. 限制 body 最大 16KB。
3. 快速判断 body 是否是 `GUAR` 信封。
4. 组装 `guard.RiskRequest`。
5. 调 `guard.Engine.Evaluate`。
6. Accept 后调用 viewlog service +1。
7. Silent 返回 204，不暴露风控细节。

Handler 不直接操作 MySQL 或 Redis，这是代码可维护性的关键边界。

## Service 层职责

Service 是当前系统业务复杂度最高的一层。它负责：

1. 业务流程编排。
2. 缓存读写和失效。
3. 外部服务调用，例如 CDN Purge、COS 上传、sitemap 刷新。
4. 事务设计和错误处理。

典型例子是文章更新：

```text
解析 articleID
  -> 查询旧文章，拿旧 tagName
  -> 确保新 tag 存在
  -> 从 Redis 读取当前浏览量，避免覆盖热值
  -> 更新 MySQL article
  -> 增量同步图片引用
  -> 删除 article Hash
  -> 删除标签统计和标签文章列表缓存
  -> 刷新 sitemap
  -> Purge CDN 文章详情 HTML
```

这也是为什么文章 service 看起来比较复杂：它不是简单 CRUD，而是在一个操作里维护数据库、Redis、CDN、sitemap、图片资产等多个状态。

后续如果要降低复杂度，可以引入领域事件，例如 `ArticleUpdated` 事件由缓存、CDN、sitemap、图片引用各自订阅处理。

## Model 层职责

Model 层封装 MySQL 操作：

1. 表结构定义。
2. 基础 CRUD。
3. Join 查询。
4. 事务内的数据一致性操作。

Model 不应该依赖 Redis、CDN、COS 或 HTTP。这样保持持久化层纯净。

典型事务：

| 方法 | 事务内容 |
|---|---|
| `SyncArticleImageReferences` | 删除当前文章旧引用、写入新引用、刷新图片使用状态。 |
| `PublishArticleDraftToPublished` | 更新已发布文章并删除编辑草稿。 |
| `DeleteArticleByID` | 删除文章和关联草稿。 |
| `CreateCommentReport` | 创建举报、统计待处理举报数、达到阈值后把评论打回待审核。 |

## 配置系统

配置由 YAML + 环境变量共同组成。

YAML 管理非敏感配置：

| 配置 | 说明 |
|---|---|
| `log` | 日志文件、轮转策略。 |
| `retry` | MySQL/Redis 初始化重试。 |
| `mysql` | 连接池和慢查询阈值。 |
| `redis` | DB 编号。 |
| `oauth` | client_id、redirect_uri 等非敏感配置。 |
| `article_image` | COS bucket、region、public_base_url。 |
| `guard` | build hash 白名单、HMAC 空白名单策略。 |
| `rate_limit` | 后台登录、评论、举报、反馈限流。 |
| `comment_moderation` | 评论审核规则。 |

敏感信息通过环境变量或 `_FILE` 注入，例如 MySQL 密码、JWT 签名密钥、OAuth secret、EdgeOne secret。

配置热更新只支持明确安全的配置段：

| 支持热更新 | 不支持热更新 |
|---|---|
| OAuth 非敏感配置、admin_info、bug_feedback、rate_limit、comment_moderation | log、retry、mysql、redis、article_image、guard、HTTP/env |

原因是后者会影响连接池、logger、外部客户端或 guard.Engine，修改后需要重建实例，不能简单替换内存结构。

## 外部基础设施封装

项目把外部服务封装到 `pkg`：

| 包 | 职责 |
|---|---|
| `pkg/cdn` | 腾讯云 EdgeOne Purge API。 |
| `pkg/cos` | 文章图片上传、删除、URL 和 object key 转换。 |
| `pkg/sitemap` | 通知 Nuxt sitemap 缓存刷新。 |
| `pkg/mailer` | Bug 反馈邮件发送。 |
| `pkg/sms` | 遗留短信验证码发送能力；当前短信登录路由已停用。 |

这样 service 只依赖业务语义接口，不直接散落 SDK 调用。

## 错误处理策略

当前错误处理有几个特点：

1. Service 返回带上下文的错误，例如 `failed to sync article image references`。
2. Handler 将错误转成统一响应码和消息。
3. 风控拒绝不一定返回错误，例如 view-log 的 Silent 决策返回 204，避免向攻击者暴露规则。
4. 外部依赖缺失时区分开发和生产，例如 CDN 未配置在非生产可跳过，生产会返回错误。
5. Redis 计数失败等非关键路径只记日志，不影响用户主流程。

## 日志与审计

日志分为：

| 类型 | 说明 |
|---|---|
| HTTP 访问日志 | Gin 中间件输出请求耗时、状态、路径。 |
| MySQL 慢查询日志 | GORM logger，默认慢查询阈值 100ms。 |
| 业务错误日志 | Service 和 Handler 中的 zap 结构化日志。 |
| guard 审计日志 | 每次风控评估记录 scene、target、decision、reason、score。 |

后续可以把日志接入 Loki/ELK，并增加 trace_id，让一次文章更新能串起 MySQL、Redis、CDN 和 sitemap 的调用链。

## 当前架构的优点

1. 单体部署简单，适合个人博客项目。
2. 分层清晰，Handler、Service、Model 职责明确。
3. Redis、CDN、COS、sitemap 等外部依赖集中封装。
4. 文章、评论、用户、风控等领域边界已经基本成型。
5. 启停生命周期考虑了缓存预热和浏览量落盘。
6. 配置系统区分敏感信息和非敏感信息，部分配置支持热更新。

## 当前架构的不足

| 问题 | 说明 |
|---|---|
| Article Service 复杂度高 | 文章操作同时维护 MySQL、Redis、图片引用、CDN、sitemap，后续应引入领域事件。 |
| 缓存操作分散 | 多个 service 手写缓存失效逻辑，容易漏删。 |
| AutoMigrate 适合开发但不适合长期生产 | 生产应引入版本化 migration。 |
| 缺少统一 trace | 目前只能通过日志排查，跨 Redis/CDN/MySQL 的链路不够直观。 |
| JSON 分享仍在 Nuxt 文件存储 | 不是 Go 后端统一管理，未来多实例部署会受限制。 |
| 部分接口响应码历史包袱 | 管理员 JWT 中间件对未授权返回 HTTP 200 + 业务码，后续可逐步规范。 |

## 后续架构优化

| 优化 | 价值 |
|---|---|
| 引入领域事件 | 文章发布、更新、删除后，由事件处理器统一做缓存、CDN、sitemap、图片引用。 |
| 抽象缓存仓储 | 把文章缓存读写集中到 repository/cache 层，减少 service 重复逻辑。 |
| 版本化 migration | 使用 goose、atlas 或 golang-migrate 管理 schema 变更。 |
| OpenTelemetry | 打通 HTTP、GORM、Redis、外部 SDK 的 trace。 |
| 持久化事件（条件式） | 仅当外部副作用失败已经成为真实可靠性问题时，再评估 Outbox；当前个人博客优先使用清晰错误、幂等重试和运维补偿，避免过早引入 worker 与事件表。 |
| 管理员操作审计 | 高风险后台操作写审计表或审计日志。 |
| 模块化单体 | 在单体内进一步明确 article/comment/user/guard 边界，为未来拆服务做准备。 |
