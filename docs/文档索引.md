## 当前系统边界

当前博客项目由四个主要工程组成：

| 工程 | 职责 |
|---|---|
| `meta-api` | Go 后端，负责文章、标签、评论、用户、后台管理、浏览量、图片资产、CDN 清理、风控评估。 |
| `portal-web` | Nuxt SSR 前台，负责博客页面、文章详情、JSON 工具、浏览量打点、JSON 分享前端入口。 |
| `admin-ui` | 后台管理系统，负责文章管理、草稿管理、图片管理、评论和用户管理。 |
| `crypto-wasm` | Rust/WASM 风控核心，负责在浏览器侧打包行为数据、混合加密并生成 guard 信封。 |

## 面试讲述主线

推荐按以下顺序准备：

1. 面试前先看 [高级 Golang 后端面试讲述提纲](./高级后端面试讲述提纲.md)，建立整体讲述主线。
2. 再讲后端整体架构：单体但按领域模块拆分，Handler、Service、Model 分层清晰，DI 统一装配。
3. 然后讲数据库设计：文章、草稿、标签、图片资产、评论、用户、管理员等核心表如何支撑业务。
4. 接着讲缓存设计：为什么文章列表和浏览量放 Redis，为什么浏览量异步回写 MySQL。
5. 再讲鉴权系统：管理员强认证、普通用户 OAuth、匿名行为 guard 三类安全边界不同。
6. 然后讲评论自动审核：为什么采用本地规则管线，如何降低误杀和支持人工复核。
7. 最后讲重点模块：CDN、浏览量、JSON 分享，以及未来从单体向可观测、高可用和微服务演进。

## 需要重点强调的设计取舍

| 设计点 | 取舍 |
|---|---|
| 文章和草稿同表 | 降低表数量和发布转换复杂度，通过 `status` 与 `published_id` 区分状态。 |
| 文章列表用 Redis ZSet | 列表排序和热门文章是高频读，ZSet 可直接按时间和浏览量分页。 |
| 浏览量先写 Redis | 避免每次访问直接更新 MySQL，降低写放大和行锁竞争。 |
| 图片资产引用增量同步 | 文章发布和更新时只同步单篇引用关系，不再做全量扫描。 |
| 评论审核本地规则管线 | 评论提交主链路不依赖外部审核 API，通过词库、结构、组合、行为和语义修正综合决策。 |
| JSON 分享 token 绑定 scope/target | 防止预检 token 被跨用途复用，避免“我的分享” token 被拿去创建分享。 |
| CDN Purge 放在 Go 后端 | 文章变更由源头服务同步清理边缘缓存，避免 Nuxt 和 CDN 状态割裂。 |
| guard 不是登录态 | guard 只证明请求具备一定浏览器行为特征，真正权限仍由业务鉴权决定。 |
