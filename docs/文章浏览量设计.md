# 文章浏览量设计

> 文档状态：当前实现
>
> 最后核对：2026-09-01
>
> 主要事实来源：`portal-web/pages/article-detail/[id].vue`、`app/service/viewlog/` 与文章缓存代码

## 设计目标

文章浏览量不是简单的 `GET /article/detail` 后直接 `+1`。当前设计目标是：

1. 尽量只统计真实用户浏览，过滤脚本、爬虫、预渲染和重复请求。
2. 不阻塞文章详情页加载，浏览量打点在客户端异步完成。
3. 不把高频浏览写入直接压到 MySQL，避免热点行更新和写放大。
4. 兼容移动端、微信内置浏览器、PC 静读、无手势浏览等真实场景。
5. 对异常请求不暴露过多风控细节，避免给攻击者调参反馈。

## 总体链路

```text
用户打开 /article-detail/{id}
  -> Nuxt SSR 渲染文章详情
  -> 客户端 onMounted 创建 BehaviorRecorder
  -> 3 秒后 useClientGuard().sign()
  -> POST /user/article/view-log/{id}
  -> Go handler 读取 GUAR 信封
  -> guard.Engine 解密、验签、评分、限流、去重
  -> Accept 后 EnsureArticleExists
  -> Redis ZINCRBY article:view:ZSet
  -> cron 定时回写 MySQL
```

## 前端触发策略

文章详情页在 `portal-web/pages/article-detail/[id].vue` 中实现浏览量打点。

核心策略：

| 策略 | 说明 |
|---|---|
| 延迟 3 秒 | 避免误触、预取、秒开秒关造成无效浏览。 |
| 只在客户端触发 | SSR 不打点，避免爬虫或服务端渲染触发计数。 |
| 同一文章单次会话只发一次 | `viewLogReportedFor` 记录当前已打点 articleId。 |
| 发送二进制信封 | body 是 `application/octet-stream`，不是普通 JSON。 |
| 使用 `fetch + keepalive` | `sendBeacon` 不支持需要 preflight 的 octet-stream。 |
| 页面不可见时 timer 路径放弃 | 后台 tab 或 prerender 不应定时打点。 |

## pagehide 和 visibility 兜底

仅靠 3 秒定时器会漏掉一些场景：

1. 用户 3 秒内关闭 tab。
2. 用户切到后台。
3. 移动端系统返回。
4. iOS BFCache 触发 pagehide。
5. 微信内置浏览器页面生命周期不完全等同普通浏览器。

因此前端增加了两个兜底触发：

| 事件 | 作用 |
|---|---|
| `visibilitychange -> hidden` | 页面进入后台前尝试发送。 |
| `pagehide` | 页面卸载或进入 BFCache 前尝试发送。 |

兜底路径会先取消定时器，再调用同一个 `sendViewLog`。同一篇文章的多条路径由 `viewLogReportedFor` 去重。

注意：如果用户停留不足 3 秒就触发兜底，后端仍可能因为 `VIEWLOG_DWELL_TOO_SHORT` 拒绝计数。这是产品口径，少于 3 秒视为无效浏览。

## 行为采集

`createBehaviorRecorder()` 会采集：

| 事件 | 说明 |
|---|---|
| `mousemove` | 50ms 节流，记录鼠标轨迹。 |
| `mousedown` / `mouseup` / `click` | 记录点击和点击停留时间。 |
| `wheel` | 80ms 节流，记录滚动方向和幅度。 |
| `keydown` / `keyup` | 记录键盘事件，不记录具体按键，减少隐私暴露。 |
| `focus` / `blur` | 记录窗口焦点变化。 |
| `visibilitychange` | 记录前后台切换。 |

序列化格式：

```text
每条事件 6B:
type(1) | dt(2, big-endian) | dx(1, i8) | dy(1, i8) | meta(1)
```

序列化时会追加 `0xff` end-marker，把 duration 推进到真实墙钟时长。这个设计是为了处理“用户打开文章后 3 秒不动鼠标、不滚动、不点击”的静读场景。如果不追加 end-marker，Rust 侧根据最后一条事件计算的 duration 可能是 0，从而误判为停留不足。

## 静读场景如何处理

用户提出过一个重要边界：微信里有人第一次打开别人分享的文章，3 秒内没有滑动和手势，也应该浏览量 +1。

当前设计对这个场景的处理是：

1. 前端 3 秒 timer 到点后发送打点。
2. recorder 即使没有真实交互，也会通过 end-marker 体现真实停留时长。
3. Rust 生成 `BehaviorSummary`。
4. 后端 L4 行为评分对 `DurationMs >= 3000` 且无交互的场景给 `NO_INTERACTION` 分数。
5. view-log 不再对行为分做硬拒，而是和 L2 浏览器环境分加权合议。
6. 真实微信 UA、语言、屏幕、导航等 L2 信号正常时，可以通过。

也就是说，当前策略不是“必须有滑动/点击才计数”，而是“停留至少 3 秒 + 浏览器环境可信 + 未触发频控和去重”即可计数。

## guard 信封

前端调用：

```ts
const { sign } = useClientGuard();
const envelope = await sign({
  scene: SCENE_VIEW_LOG,
  targetId: targetArticleId,
  recorder,
});
```

`targetId` 就是文章 ID。后端会同时校验：

1. URL path 中的 `:id`。
2. 信封 TLV 中的 `target_id`。

二者不一致时返回 `TARGET_MISMATCH`，防止拿 A 文章的信封去给 B 文章刷量。

## 后端入口

后端路由：

```text
POST /user/article/view-log/:id
```

Handler 行为：

1. 设置 `Cache-Control: no-store, private`。
2. 读取 body，限制最大 16KB。
3. 检查前 4 字节是否为 `GUAR`。
4. 采集 IP、UA、Referer、Sec-Fetch、Accept-Language。
5. 组装 `guard.RiskRequest`。
6. 调 `guard.Engine.Evaluate`。
7. Accept 后检查文章是否存在。
8. 调 viewlog service 执行 Redis +1。

响应策略：

| 决策 | 响应 |
|---|---|
| Accept | `204 No Content`。 |
| Silent | `204 No Content`，不暴露拒绝原因。 |
| BadRequest | `400 invalid token`。 |
| RateLimited | `429 rate limited`。 |
| NotFound | `404 article not found`。 |
| Internal | `500 internal error`。 |

Silent 返回 204 是风控上的取舍，避免脚本通过响应差异判断具体规则。

## 风控评分

### L1 硬拒

命中以下情况会直接拒绝：

| 规则 | 说明 |
|---|---|
| UA 黑名单 | bot、spider、headless、curl、wget 等。 |
| `perfNav=prerender` | 预渲染页面不计浏览。 |
| 非法 Sec-Fetch-Mode | 不符合浏览器请求特征。 |

### L2 浏览器环境评分

L2 从 80 分起步，结合扣分和加分项：

扣分项：

| 项 | 说明 |
|---|---|
| 语言和 Accept-Language 不一致 | 可疑脚本或伪造环境。 |
| 屏幕过小 | 非真实浏览设备特征。 |
| Sec-Fetch 或 Accept-Language 缺失 | 浏览器信号不足。 |

加分项：

| 项 | 说明 |
|---|---|
| same-origin 导航或站内 referer | 真实站内浏览信号。 |
| navigator.language 和 Accept-Language 一致 | 浏览器环境一致。 |
| 主流浏览器 UA | Chrome、Safari、Firefox、微信等。 |
| perfNav 为 navigate | 正常导航。 |

L2 低于阈值会 Silent 拒绝。

### L3 频控和去重

频控维度：

| 维度 | 说明 |
|---|---|
| IP 分钟级 | 防单 IP 高频刷。 |
| IP 小时级 | 防慢速刷。 |
| fingerprint 分钟级 | 防同浏览器高频刷。 |

去重维度：

```text
(scene, fingerprint, target_id)
```

同一 fingerprint 60 秒内对同一文章只会成功计数一次。

### L4 行为评分

行为评分使用 Rust 生成的 64B `BehaviorSummary`，关注：

| 指标 | 说明 |
|---|---|
| `DurationMs` | 停留时长。 |
| `SampleCount` | 采样数量。 |
| `MousePathLenPx` | 鼠标路径。 |
| `MouseSpeedStd` | 鼠标速度波动。 |
| `MouseJerkMean` | 鼠标抖动。 |
| `ClickCount` | 点击次数。 |
| `WheelCount` | 滚动次数。 |
| `Flags` | blur、visibility hidden 等。 |

view-log 是被动浏览场景，因此不能像表单提交一样要求强交互。当前策略：

1. 停留不足 3 秒，硬拒。
2. 停留足够但无交互，给中等分，和 L2 合议。
3. 鼠标轨迹过于机械、点击过快、键盘节奏异常等才扣分。

## Redis 计数

Accept 后只更新浏览量排序 ZSet：

```go
redisClient.ZIncrBy(ctx, cachekey.ArticleViewZSet(), 1, articleID)
```

`article:view:ZSet` 同时承担实时浏览量事实和热门文章排序。文章详情 Hash 不保存 `viewNum`，详情、列表和搜索需要展示浏览量时都读取 ZSet score。

不能对 `article:{id}:Hash` 直接执行 `HINCRBY`：当详情缓存不存在或刚被失效时，Redis 会创建一个只有 `viewNum` 的 Hash；后续列表可能把它误判为完整缓存，得到缺失字段。

失败只记录 warn，不向用户暴露。浏览量少一次比文章详情请求失败更可接受。

## MySQL 回写

回写路径在 article service：

1. cron 定时执行 `PersistViewCount`。
2. 读取 `article:view:ZSet` 全量 score。
3. 转成 `ViewNumUpdate` 列表。
4. 使用单条 `UPDATE article SET view_num = CASE id WHEN ... END WHERE id IN (...)` 批量写入。
5. 应用优雅停机时再执行一次回写。

为什么不是每次浏览直接写 MySQL：

1. MySQL 单行热点更新会造成锁竞争。
2. 浏览量是弱一致指标，不需要强事务。
3. Redis 原子自增更适合高频计数。
4. 批量回写减少数据库 RTT。

## 与 CDN 的关系

文章详情 HTML 可能被 EdgeOne 缓存。浏览量打点不能依赖 HTML 每次回源，否则缓存命中时浏览量就不会增加。

当前设计把浏览量作为客户端异步 POST：

```text
HTML 可以命中 CDN
浏览量 POST 仍直达 Go 后端
```

因此文章 HTML 缓存不会阻断浏览量统计。API 路径必须配置不缓存。

## 常见异常

| 日志原因 | 可能原因 |
|---|---|
| `HMAC_FAIL` | 浏览器加载了旧 wasm，但后端只配置了新 build_hash。 |
| `TARGET_MISMATCH` | URL articleId 和信封 targetId 不一致。 |
| `VIEWLOG_DWELL_TOO_SHORT` | 停留不足 3 秒。 |
| `L3_DEDUP` | 60 秒内同一指纹重复访问同一文章。 |
| `L3_RATE_IP` | IP 超过频控。 |
| `NO_SUMMARY` | 前端行为摘要缺失，可能是签名异常或协议问题。 |
| `TS_SKEW` | 客户端时间偏差过大。 |

## 当前设计的取舍

| 取舍 | 说明 |
|---|---|
| 3 秒后计数 | 避免误触和预渲染，但极短真实浏览不计数。 |
| Silent 返回 204 | 降低攻击者反馈，但排查时必须看日志。 |
| Redis 弱一致计数 | 性能好，但 MySQL 有延迟。 |
| 浏览量只维护在 ZSet | 避免残缺 Hash，并让计数只有一个 Redis 事实来源；读取文章数据时需要额外读取 ZSet score。 |
| 固定 WASM 路径 | 部署简单，但 CDN/微信缓存旧版本时要保留旧 build_hash。 |
| 不要求交互 | 兼容静读和微信无手势浏览，但需要 L2 环境评分兜底。 |

## 后续优化方向

| 方向 | 说明 |
|---|---|
| dirty set 回写 | 只回写浏览量变化过的文章，避免全量 ZSet 每次回写。 |
| 视图事件表 | 对部分浏览记录采样落表，用于分析来源、设备、时间段趋势。 |
| 更细粒度去重 | 结合 IP、UA、fingerprint、日期维度做日 UV 和 PV。 |
| WASM 预热 | 页面 mounted 后提前加载公钥、fingerprint 和 wasm，减少 pagehide 兜底丢失。 |
| send 队列 | 对首次 sign 慢或网络失败的情况做短暂重试，但要避免刷量。 |
| 观测指标 | 统计 Accept、Silent、HMAC_FAIL、DwellTooShort、RateLimited 比例。 |
| 微信专项兼容 | 针对微信 WebView 的生命周期和缓存行为做专项测试。 |
