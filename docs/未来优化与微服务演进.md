# 未来优化与微服务演进

> 文档状态：条件式演进方案，不代表已经实现或已排期
>
> 最后核对：2026-09-01
>
> 使用原则：只有触发条件成立、现有单体优化不足且能够承担新增运维成本时，才采用对应方案

## 当前阶段判断

当前博客系统已经不是一个简单 CRUD 项目，但仍适合保持单体：

1. 业务规模可控，个人博客读多写少。
2. 部署资源有限，单体更易维护。
3. 文章更新涉及 MySQL、Redis、CDN、sitemap、图片引用，拆服务会提前引入分布式一致性复杂度。
4. 代码内部已经有领域边界，后续可以先做模块化单体，再按需拆服务。

未来演进不应以“微服务”为目标，而应以“可观测、可灰度、可恢复、可扩展”为目标。

## 演进路线总览

推荐路线：

```text
阶段 1：模块化单体
  -> 领域事件
  -> 统一缓存层
  -> migration 管理
  -> 操作审计

阶段 2：可观测与稳定性
  -> metrics / tracing / structured logs
  -> 告警
  -> 压测基线
  -> 备份和恢复演练

阶段 3：高可用部署
  -> 多实例 stateless
  -> Redis/MySQL 高可用
  -> CDN/源站保护
  -> 健康检查和滚动发布

阶段 4：按领域拆服务
  -> 评论服务
  -> 分享服务
  -> 资产服务
  -> 搜索服务
  -> 风控服务
```

## 模块化单体优化

在拆微服务之前，先把单体内部边界做扎实。

### 领域事件

当前文章 service 复杂度高，因为一个业务动作同时维护多种副作用：

| 动作 | 副作用 |
|---|---|
| 新增文章 | 写 MySQL、写 Redis ZSet、更新标签统计、刷新 sitemap。 |
| 更新文章 | 写 MySQL、同步图片引用、删 Redis、Purge CDN、刷新 sitemap。 |
| 删除文章 | Purge CDN、清图片引用、删 MySQL、删 Redis、刷新 sitemap。 |
| 标签调整 | 更新文章 tag_id、回写浏览量、删 Redis、Purge CDN、刷新 sitemap。 |

可以引入领域事件：

```text
ArticleCreated
ArticleUpdated
ArticleDeleted
ArticleTagChanged
DraftPublished
```

事件处理器分别负责：

| Handler | 职责 |
|---|---|
| CacheInvalidationHandler | 删除或更新 Redis 缓存。 |
| CdnPurgeHandler | 清理 EdgeOne。 |
| SitemapRefreshHandler | 刷新 sitemap。 |
| ImageReferenceHandler | 同步文章图片引用。 |
| AuditHandler | 记录后台操作审计。 |

早期只在单体内同步组织事件处理器，先解决代码职责分散问题。是否异步化取决于外部副作用失败率、恢复时间目标和运维能力，不默认迁移到 outbox + queue。

### Outbox Pattern

Outbox 是备选方案，不是当前项目的默认下一步。如果文章更新成功后进程崩溃，可能出现 CDN 没有清理、sitemap 没有刷新；但个人博客后台写频率低，优先方案应是幂等操作、明确错误、人工/后台重试和失败告警。

只有同时满足以下条件时，才值得引入 Outbox：

1. 外部副作用失败已经频繁发生，人工补偿不可接受。
2. 业务要求进程崩溃后任务仍不能丢失。
3. 团队能够维护事件表、轮询 worker、重试、幂等、死信和监控。
4. 已确认简单任务表或同步重试不足以满足恢复目标。

流程：

```text
业务事务内：
  更新 article
  写 outbox_event

后台 worker：
  读取 pending event
  执行 CDN Purge / sitemap refresh / cache invalidation
  标记 success 或 retry
```

优势：

1. 事件不会因为进程崩溃丢失。
2. 可重试外部依赖失败。
3. 可记录每个副作用的执行状态。

代价是增加持久化事件模型、后台 worker、幂等协议、重试风暴控制、积压监控和数据清理。面试时应把它讲成基于可靠性目标的条件式选择，而不是为了使用架构模式。

### 版本化 migration

当前使用 GORM `AutoMigrate`，适合早期开发，但生产长期建议改为版本化 migration：

| 方案 | 说明 |
|---|---|
| goose | Go 项目常用，SQL migration 简单直接。 |
| golang-migrate | 社区成熟，支持多数据库。 |
| Atlas | schema 管理能力强，适合更规范化治理。 |

收益：

1. 每次表结构变更可审计。
2. 支持回滚计划。
3. 避免应用启动时隐式改表。
4. 多环境 schema 版本一致。

## 可观测性

高级后端面试中，可观测性是很重要的工程能力。

### Metrics

建议引入 Prometheus 指标：

| 指标 | 说明 |
|---|---|
| HTTP QPS / latency / status | 按 path 模板聚合。 |
| MySQL 慢查询数量和耗时 | 识别索引问题。 |
| Redis 命令耗时和错误数 | 缓存健康度。 |
| guard decision count | Accept、Silent、HMAC_FAIL、RateLimited 比例。 |
| view-log increment count | 浏览量成功和失败数。 |
| CDN purge count / failure | EdgeOne 清理成功率。 |
| cache hit/miss | 文章 Hash、标签、友链缓存命中率。 |
| cron duration | 浏览量回写耗时和回写数量。 |

### Tracing

引入 OpenTelemetry 后，一次文章更新可以看到完整链路：

```text
HTTP PUT /admin/auth/article/update
  -> MySQL SELECT old article
  -> MySQL UPDATE article
  -> MySQL transaction sync image refs
  -> Redis DEL article hash
  -> Redis DEL tag zsets
  -> EdgeOne CreatePurgeTask
  -> EdgeOne DescribePurgeTasks
  -> sitemap refresh
```

这对排查“后台更新成功但前台仍旧内容”非常有价值。

### 日志规范

现有 zap 日志可以继续增强：

1. 全链路 `request_id`。
2. 用户身份字段：adminID、commentUserID。
3. 业务资源字段：articleID、draftID、imageID、shareID。
4. 外部请求字段：cdn jobID、Redis key hash、MySQL table。
5. 审计日志和业务日志分开。

## 灰度发布

系统协议已经为 `crypto-wasm` 的多 `build_hashes` 灰度预留能力，但当前仓库默认配置没有启用 build hash 白名单，WASM 构建仓库和发布产物也不在本仓库中。因此下面是目标发布流程，不应表述为已经完整落地的流水线。

### WASM 灰度原则

发布 Rust/WASM 改动时：

1. 在实际 crypto-wasm 仓库提交代码，保证 git HEAD 固定。
2. 运行该仓库实际存在的构建脚本；当前文档不能从 `meta-api` 推断脚本路径。
3. 读取构建流程输出的 `guard_hmac_build_hash.txt`。
4. 后端 `guard.build_hashes` 同时保留旧 hash 和新 hash。
5. 将 wasm/js 产物同步到 `portal-web/public/guard`。
6. 发布 portal-web。
7. 发布 meta-api 配置。
8. 清理或预热 CDN。
9. 观察 `HMAC_FAIL` 是否归零。
10. 等缓存周期结束后移除旧 hash。

这个流程本质上就是前后端协议灰度兼容。

### 后端灰度

如果未来多实例部署，可以做：

| 灰度方式 | 说明 |
|---|---|
| 按实例灰度 | 新版本先启动 1 个实例，Nginx 权重 10%。 |
| 按 Header 灰度 | 内部请求或管理员请求命中新版本。 |
| 按用户灰度 | 对特定 adminID 或 fingerprint 启用新规则。 |
| 配置灰度 | guard 评分阈值、限流阈值通过配置中心灰度下发。 |

灰度必须配合指标和回滚：

1. 新版本错误率。
2. P95/P99 延迟。
3. guard 拒绝率。
4. CDN Purge 失败率。
5. MySQL/Redis 错误率。

## 高可用部署

### 应用多实例

Go 后端天然适合多实例，但要注意：

| 项 | 当前状态 | 多实例要求 |
|---|---|---|
| HTTP 服务 | 基本 stateless | 可以横向扩展。 |
| 管理员 session | Redis | 支持多实例。 |
| 普通用户 token | JWT + MySQL sessionVersion | 支持多实例。 |
| guard nonce/dedup/token | Redis | 支持多实例。 |
| 浏览量 | Redis | 支持多实例，但回写 cron 要避免重复。 |
| cron 任务 | 单进程本地 cron | 多实例需要分布式锁或独立 worker。 |
| Nuxt JSON 分享文件 | 本地文件 | 不支持多实例，需迁移。 |

最先需要处理的是 cron：如果 meta-api 多实例同时跑 `PersistViewCount`，可能重复写不一定错误，但会增加开销和竞态。建议：

1. 使用 Redis 分布式锁选主执行 cron。
2. 或者把 cron 拆成独立 worker 部署单实例。
3. 或者改成队列消费模型。

### MySQL 高可用

当前 MySQL 是核心事实来源。未来可考虑：

| 方向 | 说明 |
|---|---|
| 定期备份 | 全量备份 + binlog，验证可恢复。 |
| 主从复制 | 读写分离或灾备。 |
| 连接池治理 | max open、idle、lifetime、slow log 持续调优。 |
| DDL 规范 | 大表变更加 online DDL 或低峰执行。 |
| 慢查询看板 | 持续观察评论、搜索、后台列表等查询。 |

### Redis 高可用

当前 Redis 使用 Sentinel。未来需要：

1. 监控 master/slave 状态。
2. 监控 failover 次数。
3. 监控连接池耗尽。
4. 定期演练 Sentinel 切主。
5. 对关键短期状态设置合理 TTL，避免内存膨胀。

## 数据一致性演进

当前一致性主要靠同步调用和主动缓存失效。未来可以按风险分层：

| 数据 | 一致性要求 | 建议方案 |
|---|---|---|
| 文章正文 | 强一致 | MySQL 事务，更新失败即返回错误。 |
| 图片引用 | 中等一致 | 当前同步事务；确有跨进程恢复需求时再评估持久化任务。 |
| Redis 文章缓存 | 最终一致 | 主动失效 + 重建。 |
| CDN HTML | 最终一致但要快 | 当前同步 Purge；先补幂等重试和告警，仍不满足目标时再评估任务表或 Outbox。 |
| sitemap | 最终一致 | 异步刷新，可延迟。 |
| 浏览量 | 弱一致 | Redis 计数 + 批量回写。 |

这种分层能体现工程判断：不是所有数据都需要强一致。

## 微服务拆分建议

只有某个领域出现独立扩缩容、独立发布、独立数据治理或明确团队边界时，才考虑拆分；拆分时按领域而不是按技术层。

### 优先可拆：JSON 分享服务

原因：

1. 当前存储在 Nuxt，本身就是独立边界。
2. 有自己的配额、限流、过期清理。
3. 对博客文章核心链路影响小。

目标架构：

```text
share-service
  MySQL: share_metadata
  Object Storage: json content
  Redis: rate limit / token / quota cache
  Worker: cleanup expired shares
```

### 可拆：评论服务

评论具有独立的数据模型：

1. 评论提交。
2. 审核。
3. 举报。
4. 用户禁言。
5. 限流。

拆分后文章服务只需要暴露文章存在性，评论服务维护评论数据。

### 可拆：搜索服务

当文章数量增长，全文搜索可以独立：

```text
article-service 发布 ArticleUpdated
  -> search-service 消费事件
  -> 写 Meilisearch/Elasticsearch
  -> 前台搜索调用 search-service
```

### 可拆：资产服务

图片上传和引用关系也可以独立为资产服务：

1. 统一处理 COS/S3。
2. 管理引用关系。
3. 做图片压缩、格式转换、WebP/AVIF。
4. 做清理和回收站。

### 可拆：风控服务

guard 未来如果服务多个业务，可以成为独立风控服务：

1. 提供 `/evaluate` 接口。
2. 统一管理 build_hash、规则、阈值。
3. 输出标准风险分。
4. 和监控告警打通。

不过当前不建议过早拆，因为 guard 和 view-log/jsonshare 的业务上下文还比较紧。

## 消息队列

如果异步事件数量、吞吐或独立消费者数量确实增长，消息队列可以承载以下场景：

| 事件 | 消费者 |
|---|---|
| `ArticleCreated` | sitemap、搜索索引、RSS、缓存预热。 |
| `ArticleUpdated` | CDN Purge、搜索索引、sitemap。 |
| `ArticleDeleted` | CDN Purge、搜索删除、图片引用清理。 |
| `CommentCreated` | 审核、通知、统计。 |
| `ShareCreated` | 配额统计、审计、清理任务。 |

可选方案：

| 方案 | 适用 |
|---|---|
| Redis Streams | 部署简单，适合当前规模。 |
| NATS | 轻量消息系统，适合服务化。 |
| Kafka | 大规模日志和事件流，当前阶段偏重。 |

## 安全演进

### 管理后台

1. 增加 RBAC。
2. 管理员操作审计。
3. 登录设备管理。
4. 后台 IP 白名单。
5. 高风险操作二次确认。

### 前台用户

1. OAuth 多账号绑定。
2. 用户资料编辑和删除。
3. 评论风控和信誉分。
4. 举报滥用防护。

### guard

1. build_hash 配置热更新。
2. 原始行为流最小化或脱敏。
3. 风控规则版本化。
4. 对异常 fingerprint 做封禁。
5. 与验证码或人工验证联动。

## 性能压测和容量规划

当前仓库没有 `tests/perf` 压测工具。应先实现可重复执行的压测脚本、固定数据准备和结果记录，再讨论容量基线。建议覆盖：

| 场景 | 指标 |
|---|---|
| 首页 | 记录 P50/P95/P99、吞吐和错误率；目标值由真实用户体验和机器规格确定。 |
| 文章详情 | SSR 回源和 CDN 命中必须分开统计，不能用 CDN 数据替代源站容量。 |
| view-log | QPS、Accept 率、Redis 写耗时。 |
| 后台发布文章 | MySQL、Redis、CDN Purge 总耗时。 |
| JSON 分享 | precheck 耗时、consume 耗时、写文件耗时。 |

压测结果要区分：

1. CDN 命中性能。
2. 源站 SSR 性能。
3. Go API 性能。
4. Redis/MySQL 性能。
5. 客户端网络和压测机瓶颈。

## 面试表达建议

可以这样总结未来规划：

> 当前我不会为了“微服务”而微服务。这个项目的正确演进顺序是先把单体内部领域边界、事件机制、可观测性和发布体系做扎实。等某个模块出现独立扩缩容、独立数据治理或团队协作边界时，再拆成服务。比如 JSON 分享和评论服务最适合先拆，因为它们和文章核心链路耦合低；文章服务本身应该最后拆，因为它牵涉缓存、CDN、sitemap、搜索、图片引用等多个一致性副作用。

这个回答能体现三个点：

1. 你理解微服务不是架构装饰，而是为了解决组织、规模和独立演进问题。
2. 你能识别当前系统真正的复杂点是数据一致性和发布稳定性。
3. 你能给出从当前代码到未来架构的可执行路线。
