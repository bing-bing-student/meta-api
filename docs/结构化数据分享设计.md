# JSON 分享设计

## 业务背景

前台 `portal-web` 提供 JSON 在线工具。用户可以把当前 JSON 内容生成分享链接，也可以查看“我的分享”。这类功能有两个风险：

1. 匿名用户可以批量创建分享，消耗磁盘和带宽。
2. 分享内容可能被脚本反复提交或枚举。

当前设计把职责拆成两层：

| 层 | 职责 |
|---|---|
| Go 后端 `meta-api` | 做 guard 风控预检，签发和消费一次性 token。 |
| Nuxt SSR `portal-web` | 校验 JSON 内容和业务配额，写入文件存储和索引。 |

Go 后端不直接存储 JSON 分享内容，而是作为“是否允许继续业务”的风控前置层。

## 总体链路

```text
浏览器 JSON 工具
  -> 计算 jsonData sha256 前 32 hex 作为 targetId
  -> BehaviorRecorder 采集行为
  -> useClientGuard().sign(scene=share-create, targetId)
  -> POST meta-api /user/share/precheck?scope=create&target_id={targetId}
  -> Go guard.Engine 评估
  -> Accept 后 Redis 签发一次性 token
  -> 浏览器携带 X-Guard-Token 调 Nuxt /api/share-json
  -> Nuxt SSR 调 Go /user/share/consume?scope=create&target_id={targetId}
  -> Go GETDEL token 并校验 scope/target
  -> Nuxt 拿到 fingerprint
  -> Nuxt 执行业务限流、配额、文件写入
  -> 返回分享链接
```

查看“我的分享”也复用同一套 guard 预检，但使用不同 scope：

```text
scope=mine
target_id=00000000000000000000000000000000
```

## 为什么需要 precheck token

如果浏览器直接把 guard 信封发给 Nuxt，而 Nuxt 再把信封转发给 Go，会有几个问题：

1. Nuxt 需要理解 guard 协议或保存信封，职责变复杂。
2. JSON 实际写入接口可能被绕过预检直接调用。
3. 风控通过结果无法安全地绑定后续业务动作。

当前设计改为一次性 token：

1. 浏览器先把信封发给 Go。
2. Go 判断通过后签发 token。
3. Nuxt 写入前必须消费 token。
4. token 只能使用一次，且绑定 scope 和 targetId。

这类似“风控通行证”，Go 不接管 JSON 存储，但可以控制谁能进入存储链路。

## targetId 设计

创建分享时：

```ts
targetId = sha256(jsonData).slice(0, 32)
```

也就是 JSON 内容 hash 的前 16 字节 hex。它不用于存储主键，而是用于绑定 guard 信封和 token。

作用：

1. 防止用户拿 A 内容预检 token 去创建 B 内容分享。
2. 让 guard dedup 可以按内容目标去重。
3. 避免把完整 JSON 内容传给 Go 风控层，减少隐私面和链路体积。

“我的分享”没有具体 JSON 内容，因此使用全 0 targetId，并通过 scope 区分用途。

## scope 设计

当前 scope 有两个：

| Scope | 用途 |
|---|---|
| `create` | 创建 JSON 分享。 |
| `mine` | 查看当前 fingerprint 下的分享列表。 |

token value 中保存：

```json
{
  "fingerprint": "64 hex",
  "scope": "create",
  "target_id": "32 hex"
}
```

消费时必须同时校验：

1. token 格式是 64 hex。
2. Redis 中 token 存在且未消费。
3. claims.scope 等于请求 scope。
4. claims.target_id 等于请求 target_id。
5. fingerprint 是 64 hex。

这个设计修复了一个高优先级风险：`scope=mine` 的占位 target token 不能被拿去创建分享。

## Go 预检接口

接口：

```text
POST /user/share/precheck?scope={scope}&target_id={targetId}
Content-Type: application/octet-stream
Body: GUAR envelope
```

Handler 行为：

1. 设置 `Cache-Control: no-store, private`。
2. 校验 query 中的 `scope` 和 `target_id`。
3. 限制 body 最大 16KB。
4. 采集 IP、UA、Referer、Sec-Fetch、Accept-Language。
5. 组装 `guard.RiskRequest`，Scene 为 `share-create`。
6. 调 jsonshare service。

Service 行为：

1. 校验 scope 和 targetId。
2. 调 `guard.Engine.Evaluate`。
3. Accept 后生成 32B 随机 token，hex 后 64 字符。
4. 将 claims JSON 通过 Redis `SETNX` 写入：

```text
guard:share-create:token:{token}
TTL = 60s
```

5. 返回 token 和过期时间。

## Go 消费接口

接口：

```text
POST /user/share/consume?scope={scope}&target_id={targetId}
X-Guard-Token: {token}
```

该接口设计为 Nuxt SSR 内网调用，不应直接暴露给公网用户绕过使用。生产环境应在 Nginx 或网关层做来源限制。

消费流程：

1. 校验 token、scope、targetId 格式。
2. Redis `GETDEL guard:share-create:token:{token}`。
3. 未命中返回 401，代表 token 不存在、过期或已被消费。
4. JSON 反序列化 claims。
5. 校验 scope 和 targetId。
6. 返回 fingerprint 给 Nuxt。

`GETDEL` 是关键：它保证读取和删除原子完成，避免并发请求用同一个 token 通过两次。

## Nuxt SSR 存储设计

`portal-web/server/api/share-json.ts` 负责实际分享存储。

主要功能：

1. 读取 `X-Guard-Token`。
2. 计算本次 JSON 的 targetId。
3. 调 Go `/user/share/consume` 获取 fingerprint。
4. 校验 JSON 内容格式。
5. 校验大小、名称、密码、过期时间。
6. 按 fingerprint 做配额和限流。
7. 写入分享文件。
8. 更新 `index.json`。
9. 返回分享 URL。

当前配置：

| 配置 | 值 |
|---|---|
| 单个 JSON 最大 | 2MB。 |
| 每个 fingerprint 最多分享 | 5 个。 |
| 每个 fingerprint 最大空间 | 10MB。 |
| 最大用户数 | 10000。 |
| 创建限流 | 60 秒 3 次。 |
| 最长过期时间 | 3 天。 |
| 自动清理间隔 | 10 分钟。 |
| 存储目录 | `SHARE_STORAGE_DIR`，默认 `/tmp/shares`。 |

## 文件存储模型

当前 Nuxt 使用文件存储：

```text
SHARE_STORAGE_DIR/
  index.json
  {shareId}.json
```

单个分享文件包含：

| 字段 | 说明 |
|---|---|
| `id` | 分享 ID，32 位 hex。 |
| `jsonData` | JSON 内容。 |
| `password` | 可选密码。 |
| `expiresAt` | 可选过期时间。 |
| `createdAt` | 创建时间。 |
| `shareName` | 分享名称。 |
| `creatorFingerprint` | 创建者 fingerprint。 |
| `accessCount` | 访问次数。 |
| `lastAccessedAt` | 最近访问时间。 |

`index.json` 保存索引和总空间统计：

| 字段 | 说明 |
|---|---|
| `shares` | 分享条目列表。 |
| `totalSize` | 总大小。 |
| `lastCleanup` | 最近清理时间。 |

## 为什么当前先放在 Nuxt

JSON 工具本身主要在 `portal-web` 中实现，分享数据的读写、页面展示和工具状态都在 Nuxt SSR 侧。早期将分享存储放在 Nuxt 中有几个好处：

1. 实现成本低，前后端联调少。
2. JSON 工具是前台功能，不影响 Go 后端核心博客模块。
3. 风控能力通过 Go precheck 接入，安全边界可控。

但这只是当前阶段的工程取舍，不是长期最佳架构。

## 当前风险

| 风险 | 说明 |
|---|---|
| 文件存储不适合多实例 | 多个 Nuxt 实例之间本地文件不同步。 |
| `/tmp/shares` 默认目录不可靠 | 容器重启或宿主机清理可能丢失。 |
| 索引文件并发写风险 | 多请求同时更新 `index.json` 需要严格锁。 |
| 进程内限流不适合多实例 | 多实例时每个实例各自计数，限流失效。 |
| 过期清理依赖进程 | 进程重启后需要重新扫描或恢复 timer。 |
| 密码存储需要治理 | 如果密码明文存储，后续应改为哈希。 |

## 与 guard 的安全边界

guard 能防：

1. 简单 curl 或脚本直接打分享接口。
2. 重放旧信封。
3. 同一 fingerprint 高频创建。
4. token 跨用途复用。
5. token 并发二次消费。

guard 不能防：

1. 高级攻击者复现协议。
2. 分布式真实浏览器自动化。
3. 合法用户分享敏感内容。
4. Nuxt 存储层自身的文件并发和磁盘问题。

因此 Nuxt 业务层仍然必须保留：

1. JSON 大小限制。
2. 每 fingerprint 数量和空间限制。
3. 创建频率限制。
4. 过期清理。
5. 分享 ID 格式校验和路径穿越防护。

## 查看我的分享

“我的分享”流程：

1. 浏览器创建一个临时 recorder。
2. 等待约 50ms 给采集器留一点窗口。
3. targetId 使用 32 个 0。
4. scene 仍然是 `share-create`。
5. scope 为 `mine`。
6. precheck 通过后拿 token。
7. 调 Nuxt `/api/share-json?mine=1`。
8. Nuxt 消费 token 后拿 fingerprint。
9. 从索引中筛选 `creatorFingerprint` 匹配的分享。

后端对占位 targetId 会豁免部分行为评分和 dedup，因为列表查询没有具体内容目标，且采集窗口很短。风险通过 nonce 和频控补偿。

## 错误处理

前端区分四类 precheck 失败：

| 类型 | 说明 |
|---|---|
| `sign_failed` | 公钥、wasm、fingerprint 或签名失败。 |
| `rate_limited` | 后端返回 429。 |
| `rejected` | HTTP 200 但 token 为空，表示 Silent 拒绝。 |
| `network` | 网络异常、非 2xx、解析失败。 |

这种区分能让用户看到更准确提示，也方便排查是风控拒绝、频控还是 wasm 加载问题。

## 后续优化方向

| 方向 | 说明 |
|---|---|
| 存储迁移到 Go 后端 | Go 统一管理分享创建、读取、删除、索引和配额。 |
| MySQL + 对象存储 | 元数据入 MySQL，JSON 内容入 COS/S3，本地文件只作为缓存。 |
| Redis 限流统一化 | 创建分享和我的分享限流迁移到 Go/Redis，支持多实例。 |
| 分享密码哈希 | 使用 bcrypt/argon2 存密码哈希，不保存明文。 |
| 分享审计 | 记录创建 IP、UA、fingerprint、大小、过期时间。 |
| 异步清理 | 通过 cron 或队列清理过期分享，不依赖进程内 timer。 |
| 管理后台 | 增加分享管理、异常大文件查看、封禁 fingerprint。 |
| 内容安全扫描 | 对 JSON 内容做敏感信息提示或脱敏建议。 |
| API 内网隔离 | `/user/share/consume` 在 Nginx 层只允许 Nuxt SSR 容器访问。 |
