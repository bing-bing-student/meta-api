# 评论自动审核系统设计

本文是面试准备版，目标是讲清楚评论自动审核系统的业务价值、架构链路、工程取舍和后续演进。更细的规则、配置字段和实现细节见 [评论审核系统详细设计](./评论审核系统详细设计.md)。

## 设计目标

评论系统面对的是前台公开内容，核心风险是广告、诈骗、低俗、辱骂、联系方式引流、脚本注入和重复刷屏。自动审核系统的目标不是替代管理员，而是把评论分成三类：

| 状态 | 含义 | 处理方式 |
|---|---|---|
| `approved` | 低风险正常评论 | 直接展示。 |
| `pending` | 灰色或不确定评论 | 进入后台人工审核。 |
| `rejected` | 明确违规评论 | 不展示。 |

设计原则：

1. 评论提交主链路不依赖第三方审核 API，避免外部延迟、费用和可用性风险。
2. 审核结果必须可解释，管理员能看到命中规则、风险分类、证据和中文原因。
3. 规则必须可配置，线上治理优先改 `config/comment_moderation.yml`，减少发版。
4. 策略调整必须可回归，用黄金语料验证误杀和漏审。
5. 明确违规直接拒绝，疑似风险进入人工复核，正常评论尽量自动放行。

## 总体链路

评论提交入口：

```text
用户 OAuth 登录
  -> POST /user/comment/add
  -> CommentUserJWT 校验用户身份
  -> 校验文章存在、父评论合法、回复目标合法
  -> 检查用户是否禁言
  -> 评论提交限流
  -> moderation.Moderator 执行自动审核
  -> 写入 comment 表:
       status = approved / pending / rejected
       moderation_reasons = 审核原因
  -> 记录行为统计到 Redis
  -> 返回评论 ID 和审核状态
```

前台展示时只查询 `approved` 评论。`pending` 和 `rejected` 不会直接出现在文章详情页。

主要代码位置：

| 位置 | 说明 |
|---|---|
| `app/service/comment/user.go` | 评论提交主流程，调用自动审核并写入评论状态。 |
| `app/service/comment/moderation/` | 审核核心管线。 |
| `config/comment_moderation.yml` | 审核策略配置。 |
| `app/service/comment/admin.go` | 后台审核模拟和评论管理。 |
| `app/model/comment/comment.go` | 评论表和状态字段。 |

## 数据库模型

评论表核心字段：

| 字段 | 说明 |
|---|---|
| `article_id` | 所属文章。 |
| `parent_id` | 顶级评论为 0，回复指向顶级评论。 |
| `user_id` | 评论用户。 |
| `reply_to_user_id` / `reply_to_comment_id` | 回复目标。 |
| `content` | 评论内容。 |
| `status` | `approved`、`pending`、`rejected`。 |
| `moderation_reasons` | 审核原因，便于后台展示和复盘。 |
| `ip` | 提交来源 IP，用于审核和风控。 |

关键索引是 `(article_id, status, create_time)`，前台按文章查询已审核评论时可以高效过滤：

```text
WHERE article_id = ? AND status = 'approved'
ORDER BY create_time
```

举报表 `comment_report` 和自动审核互补：自动审核处理提交时风险，举报处理发布后的用户反馈。当同一条评论的待处理举报达到阈值时，评论会被打回 `pending`，重新进入人工审核。

## 审核管线

自动审核不是单一敏感词判断，而是一条本地规则信号管线：

```text
Raw Comment
  -> Text Normalizer
  -> Clause Segmenter
  -> Lexicon Layer
  -> Structure Layer
  -> Combination Rule Layer
  -> Behavior Layer
  -> Semantic Adjustment
  -> Decision Engine
```

### 1. 文本归一化

归一化层只生成不同视图，不直接决定审核状态。

| 视图 | 作用 |
|---|---|
| `raw` | 原始评论，便于审计。 |
| `normalized` | 去零宽字符、全半角转换、大小写统一后的文本。 |
| `compact` | 去除无意义空白，便于识别插空绕过。 |
| `pinyinFolded` | 少量拼音折叠，例如把明显绕过词转回中文。 |
| `confusable` | Unicode 同形字符骨架，防止希腊/西里尔字符混淆。 |
| `decodedTexts` | base64 URL 等解码后的候选文本。 |

这样做的原因是很多垃圾评论不会直接写敏感词，而会通过插空、全角、数字样式、同形字符、base64 URL 等方式绕过。

### 2. 词库层

词库层使用 `go-swd` 做本地敏感词基础设施，并叠加本站自定义词库。

| 等级 | 语义 |
|---|---|
| `block` | 高确定性违规，通常直接拒绝。 |
| `review` | 需要人工判断，进入待审核。 |
| `allow` | 白名单或低风险上下文。 |

为什么不能只靠敏感词：

1. 技术讨论中可能出现“垃圾回收”“注入脚本”等词，直接拦截会误杀。
2. 引流和广告常常是组合表达，不一定命中单个敏感词。
3. 重复刷屏、近重复、频率异常属于行为风险，词库看不出来。

### 3. 结构层

结构层处理不适合用词库表达的模式：

| 规则 | 例子 |
|---|---|
| URL 和混写域名 | `http://`、`xx dot com`、base64 URL。 |
| 联系方式 | 手机号、QQ、微信、进群、私信。 |
| 脚本注入 | `<script>`、事件属性等。 |
| 低质文本 | 纯符号、纯数字、重复字符。 |
| 风险短语 | 广告、代办、包过、推广等运营型风险表达。 |

这类规则比词库更适合写在代码和配置结合的结构检测里。

### 4. 组合规则

组合规则用于识别“单个词都不严重，但组合起来很可疑”的评论。

典型例子：

```text
主体词: 证书 / 账号 / API key / 代金券
行为词: 出 / 收 / 代办 / 包过 / 私聊
```

如果只看单词，“证书”“API key”可能是正常技术讨论；如果和“代办”“私聊”“包过”一起出现，风险就明显提高。

组合规则的价值是降低单词误杀，同时提高广告和诈骗识别率。

### 5. 行为风险

行为层使用 Redis 记录短期统计：

| 维度 | 说明 |
|---|---|
| 用户频率 | 同一用户短时间评论过多。 |
| IP 频率 | 同一 IP 短时间评论过多。 |
| 重复内容 | 同一用户在同一文章重复提交相同内容。 |
| 近重复内容 | 使用 SimHash 判断短时间内内容高度相似。 |

Key 通过 `cachekey.CommentModeration(...)` 统一生成，避免业务层手写 Redis key。

行为统计的写入在评论落库后执行。审核时会读取历史行为作为信号，落库后再记录本次行为，避免审核失败或非法评论污染统计。

### 6. 语义修正

语义修正是为了降低误杀。

例如：

1. 用户在讨论安全风险：“这个脚本注入漏洞怎么修？”
2. 用户引用风险词做技术说明：“垃圾回收不是垃圾广告。”
3. 用户做风险研究或举报说明。

系统会先做片段切分，再对片段级上下文做修正。一个片段是良性技术讨论，不应该压制另一个片段里的真实广告或违规内容。

这体现了一个重要工程取舍：不是“全文只要有良性词就放行”，而是按证据所在片段做保守修正。

## 决策引擎

审核信号最终进入决策引擎：

| 信号等级 | 输出 |
|---|---|
| 命中 `block` | `rejected`。 |
| 命中 `review` | `pending`。 |
| 没有风险信号 | `approved`。 |
| 审核模块异常 | 默认 `pending`。 |

异常默认 `pending` 是为了 fail safe：审核系统异常时，不应该绕过审核直接展示可疑评论。

每条风险信号包含：

| 字段 | 说明 |
|---|---|
| `source` | 信号来源，例如 lexicon、structure、behavior。 |
| `category` | 风险分类，例如 spam、abuse、contact。 |
| `level` | allow、notice、review、block。 |
| `score` | 风险分。 |
| `reason` | 机器可读原因。 |
| `evidence` | 命中的证据。 |
| `ruleID` | 规则 ID。 |
| `clause` | 命中的片段编号。 |

这些字段主要用于后台解释和策略复盘。

## 后台审核模拟

后台提供：

```text
POST /admin/auth/comment/moderation-preview
```

用途：

1. 管理员可以批量输入评论，查看审核结果。
2. 返回归一化文本、风险信号、被抑制信号和片段 trace。
3. dry-run 不创建评论，不写行为统计。
4. 如果传入 userID、articleID 或 clientIP，可以只读评估行为风险。

这个功能很适合线上治理：新增词库或调整规则前，先用模拟接口跑样例，确认误杀和漏审是否可接受。

## 举报系统与自动审核的关系

自动审核发生在评论提交时，举报发生在评论发布后。

举报链路：

```text
用户举报评论
  -> 校验用户登录
  -> 防重复举报
  -> 举报限流
  -> 写 comment_report
  -> 统计 pending 举报数量
  -> 达到阈值后把评论打回 pending
```

这解决了自动审核无法覆盖的长尾问题：即使某条评论通过了自动审核，后续用户仍然可以通过举报把它重新送回人工审核。

## 为什么采用本地规则管线

本地审核相比第三方 API 的优点：

1. 延迟可控，评论提交不用等待外部服务。
2. 可用性可控，外部 API 故障不会拖垮评论主链路。
3. 成本可控，低流量个人博客不需要额外调用费用。
4. 可解释性强，管理员能看到具体规则和证据。
5. 可以针对本站内容场景微调，例如技术词汇、博客评论风格、广告类型。

代价：

1. 泛化能力不如成熟内容安全平台。
2. 需要持续维护词库、规则和测试语料。
3. 对复杂语义和图片/多媒体内容无能为力。
4. 需要人工审核兜底。

## 缓存和一致性

评论前台只展示已审核评论，因此评论状态变化会影响文章评论列表缓存。

当前缓存设计：

| Key | 说明 |
|---|---|
| `comment:article:{articleID}:approved:list` | 单篇文章已审核评论列表缓存。 |
| `comment:moderation:behavior:*` | 评论审核行为统计。 |
| `comment:rate-limit:*` | 评论提交和举报限流。 |

当管理员修改评论状态、处理举报或评论状态从举报链路变更时，需要清理对应文章的已审核评论缓存，防止前台继续展示旧状态。

## 面试重点表达

可以这样总结：

> 这个评论审核系统不是单纯敏感词匹配，而是一个本地可解释规则管线。它先做文本归一化和片段切分，再用词库、结构、组合规则和行为统计产生风险信号，最后通过语义修正降低误杀，由决策引擎输出 approved、pending、rejected。对于不确定内容，系统不强行判断，而是进入人工审核；对于已通过但后来被举报的评论，也可以重新打回 pending。

这段话能体现：

1. 你理解内容安全不是简单关键词过滤。
2. 你有误杀和漏审的权衡意识。
3. 你把自动化和人工审核结合起来，而不是盲目追求全自动。
4. 你能从工程角度解释配置、回归测试、缓存一致性和 Redis 行为统计。

## 常见追问

### 为什么不直接用第三方内容安全 API

第三方 API 适合规模更大、风险更高的内容平台。当前博客评论量不大，本地规则能覆盖主要垃圾评论和广告风险，延迟、成本和可解释性更好。后续可以把第三方 API 作为异步复核或高风险补充，而不是同步阻塞主链路。

### 怎么降低误杀

主要靠四点：

1. 技术词和良性上下文不直接 block。
2. 对风险词做片段级语义修正。
3. 不确定内容进入 pending，而不是 rejected。
4. 调整规则前跑黄金语料回归。

### 怎么处理刷屏

刷屏不靠词库，靠 Redis 行为统计：用户频率、IP 频率、重复内容、SimHash 近重复。短期高频或近重复内容会产生 review/block 信号。

### 审核系统挂了怎么办

默认输出 `pending`，不让可疑内容绕过审核直接展示。这样会增加人工审核压力，但不会扩大前台风险。

### 后续怎么演进

1. 增加管理员审核操作审计。
2. 将规则版本和审核结果关联，方便复盘某次策略变更影响。
3. 增加规则命中指标和误杀/漏审看板。
4. 引入异步第三方内容安全复核，作为高风险补充。
5. 建立用户信誉分，对历史正常用户提高自动放行比例，对高风险用户提高待审比例。
