# 鉴权与风控系统设计

> 文档状态：当前实现；生产安全项需同时核对部署配置
>
> 最后核对：2026-09-01
>
> 主要事实来源：管理员认证、用户 OAuth、`common/guard/`、`app/di/guard.go` 与相关路由

## 总体边界

当前系统有三条不同的安全链路：

| 链路 | 使用对象 | 解决的问题 |
|---|---|---|
| 管理员鉴权 | `admin-ui` 后台管理系统 | 谁可以管理文章、草稿、图片、评论、用户、站点资料。 |
| 普通用户鉴权 | 前台评论用户 | 谁可以发表评论、举报评论、查看自己的登录状态。 |
| 匿名行为风控 | 文章浏览量、JSON 分享 | 匿名请求是否像真实浏览器行为，是否允许计数或签发分享 token。 |

这三条链路不能混为一谈。管理员和普通用户是身份认证，guard 是匿名行为校验。guard 可以降低脚本滥用，但它不是登录态，也不能替代权限系统。

## 管理员鉴权

管理员链路用于 `/admin` 路由。公开路由只包含登录、刷新 token、登出和动态码绑定/验证，真正的后台管理接口都挂在 `/admin/auth` 下，并使用 JWT 中间件。

### 路由边界

公开路由：

| 路由 | 说明 |
|---|---|
| `POST /admin/account-login` | 账号密码校验，生成二阶段登录 challenge。 |
| `POST /admin/bind-dynamic-code` | 首次绑定 TOTP。 |
| `POST /admin/verify-dynamic-code` | 已绑定用户验证 TOTP。 |
| `POST /admin/refresh-token` | 使用 refresh token 换新双 token。 |
| `POST /admin/logout` | 删除服务端 refresh 会话并清 Cookie。 |

受保护路由：

| 路由组 | 说明 |
|---|---|
| `/admin/auth/article/*` | 文章管理、草稿管理、图片管理。 |
| `/admin/auth/tag/*` | 标签管理。 |
| `/admin/auth/link/*` | 友链管理。 |
| `/admin/auth/site-dynamic/*` | 站点动态的查询、增删改和排序。 |
| `/admin/auth/comment/*` | 评论管理和举报处理。 |
| `/admin/auth/user/*` | 评论用户管理、禁言和强制登出。 |
| `/admin/auth/about-me` | 站点资料维护。 |

### 登录流程

```text
管理员输入账号密码
  -> 后端校验用户名和 bcrypt 密码
  -> Redis 写入 admin:login-challenge:{challenge}，TTL 3 分钟
  -> 如果未绑定 TOTP:
       生成 TOTP secret 和二维码
       Redis 写入 admin:pending-totp-secret:{challenge}
       用户提交动态码完成绑定
     如果已绑定 TOTP:
       用户提交动态码完成验证
  -> 生成 access_token 和 refresh_token
  -> Redis 写入 admin:session:{sessionID}
  -> 通过 HttpOnly Cookie 下发 token
```

这样设计的原因：

1. 账号密码和动态码分阶段，避免密码正确后长期停留在半登录状态。
2. challenge 有短 TTL，窗口很小。
3. TOTP 密钥首次绑定前只存在 Redis，验证通过后才写入 MySQL。
4. TOTP 校验成功后使用 Lua 原子消费 challenge、临时密钥和相关失败状态，避免同一个挑战被并发重复使用。
5. 密码使用 bcrypt，不保存明文。

### 双 Token 设计

管理员使用 access token + refresh token：

| Token | TTL | 用途 |
|---|---|---|
| access token | 10 分钟 | 访问 `/admin/auth/*` 后台接口。 |
| refresh token | 7 天 | 调 `/admin/refresh-token` 换新 token。 |

Token 使用 JWT HS256 签名，声明中包含：

| Claim | 说明 |
|---|---|
| `userID` | 管理员 ID。 |
| `tokenUse` | `admin_access` 或 `admin_refresh`。 |
| `sessionID` | 服务端会话 ID。 |
| `jti` | token 唯一 ID。 |
| `exp` / `iat` / `nbf` | 标准时间声明。 |

`access_token` 和 `refresh_token` 都通过 HttpOnly Cookie 下发。生产环境 Cookie 使用 Secure，管理员 Cookie SameSite 为 Strict，降低 CSRF 风险。

### Refresh Token 轮换

Refresh token 不只是 JWT 自校验，服务端 Redis 还保存一份会话状态：

```text
admin:session:{sessionID}
  user_id
  refresh_hash
  refresh_jti
```

刷新流程：

1. 解析 refresh token，拿到 `sessionID` 和用户 ID。
2. 对请求中的 refresh token 做 SHA-256。
3. 调用 Lua CAS，原子读取并比对 Redis 中的 `user_id` 与 `refresh_hash`。
4. 一致时在同一脚本中写入新的 `refresh_hash`、`refresh_jti` 并刷新 TTL。
5. 不一致说明 refresh token 可能被重放或已经轮换，删除会话。

这个设计可以识别“旧 refresh token 被再次使用”的情况。单纯 JWT 无状态刷新做不到这一点。

### 后台登录限流

后台登录链路使用 `common/ratelimit`，基于 Redis ZSet + Lua 实现滑动窗口，并叠加失败退避。

主要维度：

| 场景 | 维度 |
|---|---|
| 账号密码登录 | IP、用户名、用户名+IP。 |
| 绑定 TOTP | IP、challenge。 |
| 验证 TOTP | IP、challenge。 |
| 连续失败 | failure counter + lock level。 |

配置在 `config/rate_limit.yml`，生产环境建议保持开启。这样做的目的是防暴力破解和验证码枚举。

## 普通用户鉴权

普通用户只用于前台评论，不用于后台管理。当前支持 GitHub 和 Google OAuth。

### OAuth 登录流程

```text
用户点击 GitHub/Google 登录
  -> 后端生成随机 state
  -> Redis 写入 user_auth:oauth:state:{state}，TTL 5 分钟
  -> 跳转第三方 OAuth 授权页
  -> 回调时 Redis GETDEL 原子消费 state，并校验 provider
  -> 用 code 换第三方 access token
  -> 拉取第三方用户资料
  -> Upsert user 表
  -> 生成 comment_user JWT
  -> HttpOnly Cookie 写入 comment_access_token
```

`state` 中包含 provider 和回跳路径，防止 CSRF 和跨 provider 混淆。`GETDEL` 保证同一个 state 即使遇到并发回调也只能成功消费一次。

### 用户表身份模型

普通用户表使用 `(provider, provider_user_id)` 唯一约束，保证第三方账号和站内用户的一一对应关系。用户展示 handle 使用唯一索引，系统自动生成递增数字 handle，例如 `00001`。

普通用户 JWT 中包含：

| Claim | 说明 |
|---|---|
| `userID` | 站内用户 ID。 |
| `provider` | OAuth 提供方。 |
| `displayName` | 展示名。 |
| `handle` | 站内 handle。 |
| `sessionVersion` | 会话版本。 |
| `tokenUse` | 固定为 `comment_user`。 |

### sessionVersion 强制失效

普通用户没有 refresh token 体系，使用 7 天有效期的 comment token。为了支持后台强制用户登出，`user` 表中有 `session_version`。

接口校验时：

1. JWT 解析出 `sessionVersion`。
2. 后端查询用户表。
3. 如果 token 中的版本不等于数据库版本，判定会话失效。

后台强制登出时，只需要让 `session_version + 1`，旧 token 自然失效。

### 评论权限控制

普通用户登录后才能：

| 接口 | 中间件 |
|---|---|
| `POST /user/comment/add` | `CommentUserJWT` |
| `POST /user/comment/report` | `CommentUserJWT` |
| `POST /user/comment/report-status` | `CommentUserJWT` |

发表评论时还会检查：

1. 用户是否存在。
2. `sessionVersion` 是否有效。
3. 是否被禁言。
4. 文章是否存在。
5. 父评论和回复目标是否合法。
6. 评论提交限流是否通过。
7. 评论审核结果是通过、待审核还是拒绝。

## guard 匿名风控

guard 用于两个匿名场景：

| 场景 | Scene | 目标 |
|---|---|---|
| 文章浏览量 | `0x10` / `view-log` | 防止脚本刷浏览量。 |
| JSON 分享预检 | `0x20` / `share-create` | 防止脚本批量创建分享或枚举我的分享。 |

guard 的核心思想是：前端在浏览器中通过 Rust/WASM 采集行为摘要、生成二进制信封，后端解密、校验、评分和限流。

### 前端签名链路

`portal-web` 中统一使用 `useClientGuard().sign()`：

```text
collectClientMeta()
  -> navigator.language / languages
  -> screen / viewport
  -> performance navigation type
  -> timezone

createBehaviorRecorder()
  -> mousemove / click / wheel / keydown / focus / visibility
  -> 序列化为 6B/event 的二进制行为流

useClientGuard().sign()
  -> 拉取 RSA 公钥 /api/keys
  -> 获取 FingerprintJS 指纹
  -> SHA-256 拉伸为 64 hex
  -> 调 guard_core.wasm
  -> 输出 GUAR 二进制信封
```

WASM 产物部署在 `portal-web/public/guard`，浏览器通过 `/guard/guard_core.js` 和 `/guard/guard_core_bg.wasm` 加载。

### 信封结构

信封由 `crypto-wasm/src/envelope.rs` 打包：

```text
0      4     magic = "GUAR"
4      1     version = 0x01
5      1     scene
6      2     reserved
8      256   rsa_encrypted_key
264    12    aes_iv
276    16    aes_tag
292    4     ciphertext_len
296    N     ciphertext
296+N  32    build_hmac
```

明文 payload 使用 TLV 格式，包含：

| 字段 | 说明 |
|---|---|
| scene | 场景。 |
| timestamp_ms | 客户端时间戳。 |
| nonce | 一次性随机值。 |
| fingerprint_id | 浏览器指纹。 |
| target_id | 业务目标，例如文章 ID 或 JSON hash。 |
| client_meta | 语言、屏幕、导航类型等客户端元信息。 |
| behavior_summary | Rust 从行为流中计算出的 64B 摘要。 |
| behavior_raw | 原始行为流。 |
| build_hash | WASM 构建 hash。 |

### 后端评估流程

`common/guard/engine.go` 的主流程：

1. 解码信封头，校验 magic、version、scene。
2. 用 RSA 私钥解密 AES key、IV、nonce seed。
3. 用 AES-256-GCM 解密 payload。
4. 用 HMAC-SHA256 校验 `prefix || build_hash`，build hash 必须在白名单中。
5. 解析 TLV，回填 `client_meta` 到 `RiskRequest`。
6. 校验 fingerprint、target_id、timestamp。
7. Redis `SETNX` 写 nonce，防重放。
8. L1 黑名单，例如 bot、curl、headless、非法 Sec-Fetch。
9. L2 浏览器环境评分，例如语言一致性、屏幕大小、Sec-Fetch、Referer、UA、perfNav。
10. L3 频控，按 IP 和 fingerprint 控制请求速率。
11. L4 行为评分，区分浏览量和分享创建场景。
12. 成功前写 dedup，防止短时间重复计数。
13. 输出 Accept、Silent、BadRequest、RateLimited 等决策。

### build_hash 白名单

Rust 中的 `BUILD_HASH` 来自 crypto-wasm 仓库 git HEAD 前 16 hex 解码成 8 字节。构建脚本输出：

```text
pkg/guard_hmac_build_hash.txt
```

后端配置 `guard.build_hashes` 必须填写这个 16 hex，不应该填写 wasm 文件 SHA-256。灰度期间应同时保留新旧 hash，避免 CDN 或浏览器缓存中仍运行旧 WASM 导致 `HMAC_FAIL`。

生产建议：

```yaml
guard:
  build_hashes:
    - "当前新版本"
    - "上一版本灰度兼容"
  skip_hmac_when_empty: false
```

`skip_hmac_when_empty` 只适合本地开发或灰度初期，生产应显式配置 build hash。

需要如实区分“安全目标”和“当前代码保证”：当前仓库的 `config/app.yml` 尚未配置 `guard`，而 `app/di/guard.go` 在 `GuardConfig` 为空时默认 `skipHMAC=true`，所以“生产缺失配置时 fail closed”目前不是代码强制不变量。上线前应增加生产环境启动校验：build hash 为空或 `skip_hmac_when_empty=true` 时拒绝启动；在完成该改造前，它只能作为部署检查项，不能在面试中描述为已经由程序保证。

### guard 决策不是强证明

需要在面试中讲清楚：guard 能提高伪造成本，但不是绝对证明“官方 WASM 一定运行过”。

原因：

1. 前端公钥、协议、算法最终都在客户端环境中。
2. 有能力的攻击者可以逆向协议并构造请求。
3. build hash + HMAC 能保证信封与某个已知构建逻辑一致，但不能证明执行环境可信。

因此服务端仍然需要：

1. nonce 防重放。
2. target 绑定。
3. fingerprint 和 IP 频控。
4. dedup。
5. 行为评分。
6. 审计日志。
7. 对业务动作设置配额。

## JSON 分享 token 绑定

JSON 分享不是 guard 通过后直接写数据，而是先签发一次性 token：

```text
浏览器 POST /user/share/precheck?scope=create&target_id=<jsonHash>
  -> guard.Engine.Evaluate
  -> Accept 后 Redis SETNX guard:share-create:token:{token}
  -> value = {"fingerprint":"...","scope":"create","target_id":"..."}
  -> 返回 token

Nuxt SSR POST /api/share-json
  -> 携带 X-Guard-Token
  -> 调 Go /user/share/consume?scope=create&target_id=<jsonHash>
  -> Redis GETDEL token
  -> 校验 scope/target_id
  -> 返回 fingerprint
  -> Nuxt 继续执行业务限流和文件写入
```

这样设计解决了一个关键风险：预检 token 不能跨用途复用。例如“我的分享”使用 `scope=mine` 和全 0 targetId，不能拿去创建分享。

## 审计与故障排查

guard 每次评估都会记录 `guard_eval` 日志，字段包括：

| 字段 | 说明 |
|---|---|
| `scene` | `view-log` 或 `share-create`。 |
| `target_id` | 文章 ID 或 JSON targetId。 |
| `fingerprint_id` | 解密出的 fingerprint。 |
| `ip` / `user_agent` | 请求来源。 |
| `decision` | 决策枚举。 |
| `reject_reason` | 拒绝原因，例如 `HMAC_FAIL`、`L3_DEDUP`。 |
| `score` | 评分。 |
| `client_ts` / `server_ts` | 时间戳。 |

常见问题：

| 现象 | 可能原因 |
|---|---|
| `HMAC_FAIL` | 后端 `build_hashes` 未包含当前浏览器加载的 WASM 版本。 |
| `TARGET_MISMATCH` | URL 中的 articleId 或 share target 与信封内 target 不一致。 |
| `TS_SKEW` | 客户端时间和服务端时间偏差超过 2 分钟。 |
| `NONCE_REPLAY` | 同一信封被重复提交。 |
| `L3_DEDUP` | 同一 fingerprint 短时间重复访问同一目标。 |
| `VIEWLOG_DWELL_TOO_SHORT` | 浏览停留不足 3 秒。 |

## 后续优化方向

| 方向 | 说明 |
|---|---|
| 管理员角色权限 | 当前管理员是单角色，后续可拆 RBAC，例如文章编辑、评论审核、系统配置。 |
| 管理员操作审计 | 记录文章发布、删除、标签调整、用户禁言等高风险操作。 |
| Refresh token 设备管理 | 展示当前登录设备，支持单设备登出和全设备登出。 |
| OAuth 账号绑定 | 支持同一站内用户绑定多个 provider。 |
| guard 配置热更新 | build hash、频控阈值、评分阈值可接入配置中心。 |
| guard 风险分层 | 对低风险请求放行，高风险进入验证码或延迟队列，而不只是静默拒。 |
| 原始行为流治理 | 当前后端主要消费 summary，后续要么删除 raw 降低隐私面，要么明确用于高级模型。 |
| 内网接口隔离 | `/user/share/consume` 仅应允许 Nuxt SSR 内网调用，可在 Nginx 或网关层限制来源。 |
