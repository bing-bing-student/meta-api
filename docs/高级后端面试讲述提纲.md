# 高级 Golang 后端面试讲述提纲

这份文档用于面试前快速复盘。完整设计细节分散在 [数据库设计](./数据库设计.md)、[缓存设计](./缓存设计.md)、[鉴权与风控系统设计](./鉴权与风控系统设计.md)、[后端代码架构](./后端代码架构.md)、[CDN 与边缘缓存设计](./内容分发网络与边缘缓存设计.md)、[文章浏览量设计](./文章浏览量设计.md)、[JSON 分享设计](./结构化数据分享设计.md)、[评论自动审核系统设计](./评论自动审核系统设计.md) 和 [未来优化与微服务演进](./未来优化与微服务演进.md) 中；本文件只提炼讲述顺序、核心亮点和常见追问。

## 一句话介绍项目

这是一个 Go 单体博客后端，配套 Nuxt SSR 前台、后台管理系统和 Rust/WASM 风控组件。后端负责文章、草稿、图片资产、评论、评论自动审核、普通用户 OAuth、管理员双 token 鉴权、浏览量风控计数、JSON 分享预检、Redis 缓存、CDN Purge 和 sitemap 刷新。

可以这样开场：

> 这个项目不是简单 CRUD。文章发布或更新会同时影响 MySQL、Redis 缓存、图片引用关系、EdgeOne CDN、Nuxt sitemap 和前端 WASM 风控协议。我主要关注的是把单体内部的领域边界、缓存一致性、鉴权安全和发布灰度做好。

## 推荐讲述顺序

1. 后端整体架构：Gin + Service + Model + DI，为什么当前仍然是单体。
2. 数据库设计：文章/草稿同表、图片资产引用表、评论/举报/用户/管理员表。
3. 缓存设计：文章 ZSet + Hash、浏览量 Redis 计数、短期状态和限流。
4. 鉴权系统：管理员强认证、普通用户 OAuth、匿名 guard 风控三条边界。
5. 评论自动审核：本地规则管线、行为风险、人工复核、可配置和可回归。
6. 重点模块：CDN、浏览量、JSON 分享。
7. 演进方向：模块化单体、可观测性、灰度发布、高可用和微服务拆分。

## 架构亮点

| 亮点 | 面试表达 |
|---|---|
| 模块化单体 | 当前访问规模和团队规模不需要提前微服务化，但包边界已经按 article/comment/user/guard 等领域拆开。 |
| 显式 DI | 使用 dig 注入 MySQL、Redis、KeyManager、CDN、COS、Model、Service 和 Handler，依赖关系集中管理。 |
| 启停生命周期 | 启动时预热文章 ZSet，运行时 cron 回写浏览量，停机时再兜底持久化。 |
| 缓存主动失效 | 文章和标签更新时主动清 Redis 和 CDN，而不是只依赖 TTL。 |
| 弱一致分层 | 文章正文强一致，CDN/sitemap 最终一致，浏览量弱一致。不同数据采用不同一致性策略。 |

## 数据库设计怎么讲

重点讲 `article` 表和图片资产表。

`article` 同时存发布文章和草稿：

| 状态 | 表示 | 发布逻辑 |
|---|---|---|
| 已发布文章 | `status=published` | 前台可见。 |
| 新草稿 | `status=draft` 且 `published_id IS NULL` | 发布时直接把当前记录转为 published。 |
| 编辑草稿 | `status=draft` 且 `published_id=<原文章ID>` | 发布时事务内更新原文章并删除草稿。 |

这个设计的回答重点：

1. 避免文章和草稿两套表结构长期漂移。
2. 编辑草稿不影响线上已发布文章。
3. `published_id` 唯一索引限制同一文章只有一个编辑草稿。
4. 查询必须显式带 `status`，这是同表设计的主要约束。

图片资产使用 `article_image` 和 `article_image_reference`：

1. `object_key` 唯一，保证同一个 COS 对象只有一条资产记录。
2. 引用表记录 `image_id + article_id + ref_type + ref_count`。
3. 发布/更新文章时只解析当前文章正文做增量同步，不保留全量扫描接口。
4. 删除图片前检查引用数量，防止仍被文章使用的图片被物理删除。

## 索引优化怎么讲

当前业务量不大，所以索引设计偏克制：

| 表 | 关键索引 | 原因 |
|---|---|---|
| `article` | `id`、`status`、`tag_id`、`published_id` | 详情、列表过滤、标签文章、编辑草稿唯一性。 |
| `article_image` | `object_key` unique、`status` | 上传幂等和后台筛选。 |
| `article_image_reference` | `(image_id, article_id, ref_type)` unique、`article_id` | 防重复引用行，支持图片详情和文章更新清理。 |
| `user` | `(provider, provider_user_id)` unique、`handle` unique | OAuth 身份唯一和展示 handle 唯一。 |
| `comment` | `(article_id, status, create_time)`、`parent_id` | 前台按文章查已审核评论和楼中楼回复。 |
| `comment_report` | `(comment_id, reporter_id)` unique、`status`、`create_time` | 防重复举报和后台处理待审核举报。 |

如果被问为什么搜索不用全文索引：

> 当前线上文章量很小，标题和正文 `LIKE` 的成本可控。过早引入 Elasticsearch 会增加部署和一致性成本。真正文章量上来后，可以先 MySQL FULLTEXT，再按需求演进到 Meilisearch 或 Elasticsearch。

## 缓存设计怎么讲

核心是 Redis ZSet + Hash：

```text
article:time:ZSet      按发布时间排序
article:view:ZSet      按浏览量排序
article:{id}:Hash      文章详情字段
tag:articleNum:ZSet    标签文章数
{tagName}:article:ZSet 标签下文章列表
```

为什么这样设计：

1. 首页、归档、热门文章都是高频读。
2. ZSet 天然支持排序分页。
3. 文章详情 Hash 可以按需回填。
4. 浏览量用 `ZINCRBY` 更新热门排序，不需要查库聚合。
5. MySQL 仍是事实来源，Redis 是热点视图。

浏览量为什么不直接写 MySQL：

1. 热门文章会形成单行热点更新。
2. 每次浏览都 `UPDATE` 会增加写放大和锁竞争。
3. 浏览量是弱一致指标，允许延迟落库。
4. Redis 原子自增更适合高频计数。

## 鉴权系统怎么讲

要明确三条边界：

| 链路 | 本质 | 保护对象 |
|---|---|---|
| 管理员鉴权 | 强身份认证 | 后台管理接口。 |
| 普通用户 OAuth | 评论用户身份 | 评论、举报、个人登录状态。 |
| guard 风控 | 匿名行为可信度判断 | 浏览量和 JSON 分享。 |

管理员链路亮点：

1. 账号密码 + TOTP 二阶段登录。
2. access token + refresh token 双 token。
3. refresh token 服务端 Redis 会话，刷新时滚动 hash。
4. 旧 refresh token 重放会触发会话删除。
5. Cookie 使用 HttpOnly，生产 Secure。

普通用户链路亮点：

1. OAuth state 放 Redis，防 CSRF。
2. `(provider, provider_user_id)` 唯一。
3. `session_version` 支持后台强制登出。
4. 评论接口还会叠加禁言、限流和审核。

guard 风控要强调：

> guard 不是登录态，也不是绝对安全证明。它提高伪造和批量滥用成本，真正的安全边界仍然在服务端 nonce、target 绑定、频控、去重、行为评分和业务配额。

## 评论自动审核模块怎么讲

评论审核的核心目标不是“把所有风险评论直接拒绝”，而是在低成本、低延迟的前提下，把正常评论自动放行，把明确违规内容拒绝，把灰色内容送入人工审核。

提交链路：

```text
用户 OAuth 登录
  -> POST /user/comment/add
  -> 校验文章、父评论、回复目标、禁言和限流
  -> moderation.Moderator 执行本地审核管线
  -> 写入 comment.status 和 moderation_reasons
  -> 记录行为统计
  -> 前台只展示 approved 评论
```

审核管线：

| 层 | 作用 |
|---|---|
| 文本归一化 | 去零宽字符、全半角转换、大小写统一、数字样式归一化、生成 compact/pinyin/confusable 视图。 |
| 词库检测 | 使用 go-swd 内置词库和自定义词库，区分 block、review、allow。 |
| 结构检测 | 识别 URL、联系方式、script 注入、低质文本、风险短语。 |
| 组合规则 | 用“主体词 + 行为词”等组合降低单词误杀，提高广告、诈骗等场景识别率。 |
| 行为风险 | 基于 Redis 统计用户频率、IP 频率、重复内容和 SimHash 近重复。 |
| 语义修正 | 对引用、技术讨论、风险研究等良性片段抑制误伤信号。 |
| 决策引擎 | 输出 `approved`、`pending`、`rejected`，并保存中文可解释原因。 |

面试时重点讲三个取舍：

1. 本地优先：评论提交主链路不依赖第三方审核 API，避免外部延迟和可用性风险。
2. 可解释：后台能看到命中来源、分类、规则 ID、证据、片段和中文原因。
3. 可回归：敏感词、结构规则、组合规则和语义修正都通过黄金语料回归，避免策略调整后误杀扩大。

为什么不是只靠敏感词：

> 敏感词只能解决显式词命中，容易误杀技术语境，也识别不了变体、联系方式、重复刷屏和组合式广告。当前设计把词库当成基础信号，再叠加结构、组合、行为和语义修正，最后统一决策。

人工介入：

1. `approved` 直接展示。
2. `pending` 进入后台评论管理，由管理员审核。
3. `rejected` 直接拒绝展示。
4. 用户举报达到阈值后，已展示评论会被打回 `pending`。
5. 后台提供 `moderation-preview` dry-run，管理员可批量模拟审核，不写入评论和行为统计。

## 浏览量模块怎么讲

链路：

```text
用户打开文章详情
  -> 前端 3 秒后采集行为并调用 Rust/WASM sign
  -> 生成 GUAR 二进制信封
  -> POST /user/article/view-log/{id}
  -> Go guard 解密、验 HMAC、校验 target、评分、限流、去重
  -> Accept 后 Redis HINCRBY + ZINCRBY
  -> cron 批量回写 MySQL
```

重点设计：

1. HTML 可被 CDN 缓存，浏览量打点仍通过 API 直达后端。
2. `target_id` 绑定文章 ID，防止拿 A 文章信封刷 B 文章。
3. 静读场景不强制要求滑动或点击，只要停留足够且浏览器环境可信即可通过。
4. `HMAC_FAIL` 常见原因是浏览器或微信缓存旧 wasm，但后端只配置新 build hash。
5. 发布 Rust/WASM 时后端 `build_hashes` 必须保留新旧两版。

## JSON 分享模块怎么讲

链路：

```text
浏览器计算 JSON hash 前 32 hex 作为 targetId
  -> guard precheck
  -> Go 签发一次性 token
  -> 浏览器携 token 调 Nuxt 分享接口
  -> Nuxt 调 Go consume
  -> Go GETDEL token 并校验 scope/target
  -> Nuxt 执行 JSON 校验、配额、文件写入
```

为什么 token 要绑定 `scope + target_id + fingerprint`：

1. 防止“我的分享”预检 token 被拿去创建分享。
2. 防止 A JSON 的预检 token 被拿去创建 B JSON。
3. `GETDEL` 保证 token 只能消费一次。
4. Go 不保存 JSON 内容，减少隐私面。

当前风险也要主动讲：

1. JSON 分享仍在 Nuxt 本地文件存储，不适合多实例。
2. 限流和索引文件并发写需要后续迁移到 Go + Redis/MySQL。
3. 长期应改成 MySQL 存元数据、对象存储存 JSON 内容。

## CDN 设计怎么讲

CDN 重点是 Nuxt SSR 无后缀页面：

1. 静态资源可以按后缀或路径长缓存。
2. `/article-detail/*` 是无后缀 HTML，必须单独配置路径缓存规则。
3. API 必须 no-store，尤其是 view-log、share precheck、admin API。
4. 文章更新、删除、编辑草稿发布后由 Go 后端主动 Purge CDN。
5. 删除文章时先 Purge 再删库，是偏保守的一致性策略，避免 CDN 继续返回已删除内容。

源站保护要讲得克制：

> 默认 server 返回 444 或拒绝握手只能减少业务特征，不等于完全隐藏源站。更完整的方案是云防火墙只放行 EdgeOne 回源 IP、Nginx 校验回源 Header、默认 server 不返回业务内容，并把 reject/default 日志单独记录。

## 未来演进怎么讲

不要上来就说“拆微服务”。推荐回答：

> 当前正确路线是先做模块化单体和工程治理，再按独立扩缩容、独立数据治理、独立发布的需求拆服务。

优先级：

1. 领域事件：把文章更新后的缓存、CDN、sitemap、图片引用副作用拆成事件处理器。
2. Outbox：避免 MySQL 成功但 CDN Purge/sitemap 刷新丢失。
3. 版本化 migration：替代长期生产环境的隐式 AutoMigrate。
4. 可观测性：Prometheus + OpenTelemetry + 结构化审计日志。
5. 高可用：多实例、Redis 分布式锁控制 cron、MySQL 备份恢复演练。
6. 服务拆分：优先 JSON 分享服务、评论服务、搜索服务、资产服务，文章服务最后拆。

## 常见追问回答

### 为什么现在不拆微服务

因为当前复杂点不是单机性能，而是文章变更带来的多副作用一致性。过早拆服务会引入分布式事务、跨服务事件、部署和监控成本。先把单体内部边界和 outbox 做好，比直接拆更稳。

### Redis 挂了怎么办

文章 ZSet 可以启动时从 MySQL 预热恢复，文章 Hash 可以按需回填。短期状态如登录 challenge、OAuth state、guard nonce 会受影响，这类数据本来就依赖 Redis，需要 Redis Sentinel、告警和故障演练。浏览量如果 Redis 完全不可用，会丢部分弱一致计数，但不会影响文章正文读取。

### CDN Purge 失败怎么办

当前文章删除采用保守策略，Purge 失败就不继续删除，避免 CDN 长期展示已删除内容。未来可以用 outbox 记录 Purge 任务，支持重试、告警和后台任务状态展示。

### guard 是否能防高级攻击者

不能作为强证明。客户端协议最终可逆向。guard 的价值是提高普通脚本和批量滥用成本，并为服务端频控、去重、评分和审计提供输入。

### 文章浏览量为什么可能不加

常见原因是停留不足 3 秒、同一 fingerprint 60 秒内重复访问、IP/fingerprint 频控、target 不匹配、客户端时间偏移，或者 Rust/WASM build hash 与后端白名单不一致导致 `HMAC_FAIL`。

### 生产为什么不长期依赖 AutoMigrate

AutoMigrate 对早期开发很方便，但生产需要可审计、可回滚、可灰度的 schema 变更。长期应使用 goose、golang-migrate 或 Atlas，把 DDL 变成版本化 migration。
